1. 一句话结论与仓库概况

AccelForge 的代码揭示了论文里没写的核心机制：成本模型对每个"映射模板"只符号化地跑一次，输出以 tile 形状为自变量的 sympy 表达式；mapper 用导数判定目标函数对每个 tile 变量的单调性来剪枝，再用 lambdify 把表达式编译成 numpy 向量函数批量求值。跨算子的融合决策则靠"每个 Einsum 先求 Pareto 前沿，再按兼容性从左到右拼接"完成——模型和 mapper 共用同一套 pmapping / join 基础设施，evaluate_mapping 本质上就是"每个 Einsum 只有一个候选的 mapper"。

2. 仓库地图：五个子包与它们的依赖方向

accelforge/ 包下的五个子包职责清晰：frontend 定义全部输入数据模型（Pydantic），mapper/FFM 实现搜索，model/_looptree 实现成本评估，plotting 做结果可视化，util 提供并行、表达式求值、frozenset 等基础设施。依赖方向基本是 mapper → model → frontend → util，但 model/main.py 反向导入了 mapper/FFM/_join_pmappings——因为模型评估复用了 mapper 的 join 机制（见第 3 节）。

图 1 · 仓库目录与子包依赖。frontend 是所有子包的公共底座；mapper 与 model 之间存在双向依赖（红色虚线），这不是设计失误，而是"模型即单候选 mapper"这一架构选择的直接后果。

3. 两条主路径：map_workload_to_arch 与 evaluate_mapping

frontend/spec.py 里的 Spec 类只暴露两个高层动词。map_workload_to_arch() 走 mapper/FFM/main.py：生成 pmapping → join → 对最终映射逐个详细评估。evaluate_mapping() 走 model/main.py：把用户手写的 spec.mapping 在 Split 节点处切成每个 Einsum 的 pmapping，对每个跑 run_model 得到一行数据帧，然后调用与 mapper 完全相同的 clean_compress_and_join_pmappings(for_model=True) 拼成总结果。

图 2 · 两条主路径共享 pmapping 数据帧格式与 join 代码。右侧 ③ 对应 model/main.py:69，左侧 ③ 调用右侧整条路径（mapper/FFM/main.py:116）。这种"模型是 mapper 的退化情形"设计保证了评估一致性，代价是模块间出现循环依赖。

数据帧列名约定（_pareto_df/df_convention.py）值得记住：Total<SEP>energy、Total<SEP>latency 是目标列；<Einsum><SEP>mapping 存 pmapping 对象 ID；reservation<SEP><memory><SEP><level> 存某存储在某循环层级的占用比例；usage<SEP>… 存空间阵列利用率。join 阶段的 Pareto 比较、兼容性匹配、资源超额检查全部通过列名前缀分派。

4. Spec 前端：Pydantic 模型与表达式求值管线

Spec（frontend/spec.py:33）有 8 个字段：arch、mapping、workload、variables、config、renames、mapper（FFM 配置）、model（模型配置）。所有字段都是 EvalableModel（util/_basetypes.py）的子类——Pydantic 模型加一层"字符串表达式延迟求值"。YAML 里几乎任何数值位置都可以写 Python 表达式（如 size: 1024 * 1024、throughput: 32 * 200e6），求值时按固定顺序构建符号表：

图 3 · 表达式求值的符号表累积顺序。顺序本身就是语义：variables 能被 renames 引用，workload 能被 arch 引用，反之不行。tags 机制让架构描述里可以写 energy: 2 if is_attention else 1 这类按 Einsum 变化的成本。

YAML 加载层叠了两套模板：Jinja2（{% set %}、{% for %}、{{include_text()}}）在解析前展开文本，用于 LLM 负载的参数化（例如 multi_head.yaml 用 DECODE 变量切换 prefill / decode 的 Einsum 形态）；YAML 标签（!Memory、!Compute、!Storage、!Temporal…）由 util/_yaml.py 映射到 Pydantic 类的 Tag 判别联合（structure.py:226）。

5. 架构描述：节点类型、YAML 语法与扁平化

架构是一棵节点树（frontend/arch/structure.py + components.py）。顶层 Arch 继承 Hierarchical，其 nodes 列表从上到下就是存储层级。叶子有四类可计费组件（Memory / Toll / Compute / Network）加一个纯结构节点 Container；分支有 Hierarchical、Array（带空间扇出）、Fork（旁路分支）。

图 4 · 架构节点类层次（frontend/arch/）。Spatialable 是 mixin，让 Container、Component、Array 都能声明 spatial: [{name, fanout, reuse}]。四种可计费叶子中 Memory 与 Toll 的区别是"是否允许时间复用"——这决定了模型里是否为它分配 Buffet。

示例：eyeriss.yaml 的节点树

# examples/arches/eyeriss.yaml（节选）
arch:
  extra_attributes_for_all_component_models: {tech_node: 65e-9}
  nodes:
  - !Memory  name: MainMemory    component_class: LPDDR4   size: inf
             tensors: {keep: ~Intermediates, may_keep: All}
  - !Memory  name: GlobalBuffer  component_class: SmartBufferSRAM
             size: 1024 * 1024   extra_attributes_for_component_model: {n_banks: 32}
             actions: [{name: read, bits_per_action: 64, throughput: 32 * 200e6}, …]
             tensors: {keep: ~MainMemory, may_keep: All}
  - !Container name: ProcessingElement
             spatial:
             - {name: reuse_weight, fanout: 14, reuse: weight, min_usage: 1}
             - {name: reuse_output, fanout: 12, reuse: output, min_usage: 1}
  - !Memory  name: InputScratchpad   size: 12 * 16   tensors: {keep: input}
  - !Memory  name: WeightScratchpad  size: 192 * 16  tensors: {keep: weight}
  - !Memory  name: OutputScratchpad  size: 16 * 16   tensors: {keep: output}
  - !Compute name: MAC  component_class: IntMAC  actions: [{name: compute, throughput: 200e6}]
             extra_attributes_for_component_model: {multiplier_width: 8, adder_width: 16}

几个值得注意的语法点：tensors: {keep, may_keep} 用集合表达式（~Intermediates、~MainMemory、input）声明每级存储必须 / 可以持有哪些张量，这是 mapper 的 dataplacement 约束来源；Container 上的 spatial 用 reuse: weight 声明该维度上哪个张量被广播复用（Eyeriss 的行固定数据流）；min_usage: 1 要求阵列必须被占满。整个描述只有 56 行，比 Timeloop 的三文件格式紧凑得多。

图 5 · 架构扁平化。树被拆成若干条"从根到某个 Compute"的线性路径，mapper 和 model 后续只处理线性路径。异构（CiM + 数字 MAC）就是多条路径，论文 Table I 里 AccelForge 独有的"Heterogeneous"能力在代码层面只是这一步的副产品。

6. 工作负载：Einsum 级联、投影与 renames

frontend/workload.py 的 Workload 是一个 Einsum 列表加公共元数据。Einsum 有两种写法：字符串 "Z[m,n] = A[m,k] * B[k,n]"（transformer 示例全部用此法），或显式 tensor_accesses 列表（每项给 name、projection、output）。rank_sizes 或 iteration_space_shape（ISL 表达式）定义迭代空间，bits_per_value 与 persistent_tensors 用集合表达式批量设置。 

# examples/workloads/transformers/_attention_decode_types/multi_head.yaml（节选）
workload:
  rank_sizes: {P: {{N_CONTEXT_TOKENS}}, M: {{N_NEW_TOKENS}}, B: …, H: …, E: …, D: …}
  bits_per_value: {All: 8}
  persistent_tensors: weight - Intermediates
  einsums:
  - {einsum: "I[b, m, d] = I_in[b, m, d]", is_copy_operation: True}
  - "V[b, m, h, e] = I[b, m, d] * WV[h, e, d]"
  - "K[b, m, h, e] = I[b, m, d] * WK[h, e, d]"
  - "Q[b, m, h, e] = I[b, m, d] * WQ[h, e, d]"
  - einsum: "QK[b, m, p, h] = Q[b, m, h, e] * K_cache[b, P: p, h, e]"
    renames: {input: Q}
  - "QK_softmax[b, m, p, h] = QK[b, m, p, h]"
  - "AV[b, m, h, f] = QK_softmax[b, m, p, h] * V_cache[b, P: p, h, E: f]"
  - "Z[b, m, g] = AV[b, m, h, f] * WZ[h, f, g]"

图 6 · 工作负载是 Einsum 级联，中间张量（同时作为输出和输入）是融合的唯一载体。renames 让架构描述用抽象角色（input / output / weight）而不是具体张量名写约束，一份架构 YAML 就能跑所有示例负载。

7. 映射 IR：节点类型与"融合 = 绕过外层存储"

frontend/mapping/mapping.py（约 1700 行）定义了映射的节点代数。一个 Mapping 就是一个 Nested 节点列表，从外到内依次是存储放置、循环、最后以 Compute 叶子收尾；多 Einsum 用 Sequential（或 Pipeline）分支。

图 7 · 一个两算子融合映射的节点树，以及论文中 Fusion / Uneven / Hybrid 三个概念在映射 IR 里的落点。核心观察：AccelForge 没有"融合模式"，融合只是中间张量的 Storage 节点出现在某个共享循环之下、且不出现在最外层存储——这把跨算子优化压缩成了一个与单算子 dataplacement 同构的决策。

8. FFM mapper 管线：从模板到 Pareto 前沿

mapper/FFM/ 是仓库最复杂的部分。论文把 mapper 分成 Intra-Einsum（TCM）和 Inter-Einsum（FFM）两级，但代码里没有名为 TCM 的独立模块——整个 mapper/FFM/ 包就是 FFM，其中 _make_pmappings/ 子包承担 intra-Einsum 职责，_join_pmappings/ 承担 inter-Einsum 职责。

图 8 · FFM 的 11 步管线。阶段 A 对每个 Einsum 独立求 Pareto 前沿（并行度 = Einsum 数 × Compute 路径数 × 模板分片数），阶段 B 把它们拼成全负载映射。论文里的"TCM"对应 ⑤，"FFM"对应 ⑧–⑪，但代码里是一个包。

模板枚举（②）在枚举什么

  1. make_storages / make_storage_order：对每个张量决定它在扁平化路径上的哪些存储出现（受 tensors: {keep, may_keep} 约束），以及各张量 Storage 节点的相对顺序——这一步同时产生 Uneven（各张量不同深度）与融合（中间张量跳过外层存储）两类候选。
  2. make_loops：在 Storage 节点之间插入 Temporal / Spatial 循环的骨架（哪个 rank 变量、在哪一层、是否空间展开），tile 形状留作符号。place_missing_temporal_loops（make_pmapping_templates.py:90）保证每个 rank 变量至少有一个循环；remove_unordered_spatial_temporal_loops 剔除等价排列。
  3. make_reservations：为每个张量在每个持有它的存储插入 Reservation 占位，后续模型据此算占用。
  4. constraints（_make_pmappings/contraints/，目录名拼写如此）：把 arch 上的 min_usage、tile 形状、循环边界约束编译成 lambda 过滤器。

模板不含循环边界（文档 definitions.rst 对 "Pmapping Template" 的定义正是如此），所以一个模板对应一个 tile 形状的连续搜索空间。这是把搜索分成"离散结构枚举 + 连续形状优化"两层的关键设计。

9. 核心技巧一：符号化建模与单调性剪枝

这是代码里最有分量、论文概览稿完全没提的机制。model/run_model.py:34 的 run_model(job) 返回的数据帧里，Total<SEP>energy、Total<SEP>latency、各 reservation 列的值不是数字而是 sympy 表达式，自变量是 insert_sympy_symbols（_symbolic.py:161）为每个循环的 tile 形状创建的符号。

图 9 · 符号化建模管线。②→③ 把成本模型变成关于 tile 符号的闭式表达式，④ 用微积分而不是采样判断哪些维度不需要搜索，⑥ 把剩余搜索变成向量化数值计算。这解释了论文"orders of magnitude less time"的来源，也解释了为什么 make_tile_shapes.py 要 2700 行。

这个设计的代价写在 assumptions.rst 里：每个动作能耗恒定、不依赖状态；数据恰好准时到达、无双缓冲；每个 Einsum 内所有延迟完美重叠（总延迟 = 各组件最大值）。这些假设不是建模粗糙，而是为了让成本函数可微、可单调性分析而必须做的简化。任何引入状态依赖（如 bank 冲突、缓存命中率）的扩展都会破坏 ④ 的前提。

10. 核心技巧二：Compatibility 与脏-净两阶段 Join

跨 Einsum 拼接的正确性靠 _join_pmappings/compatibility.py 的 Compatibility 对象保证。文件头部注释（:34–39）给出了三条抽象：每个张量存储在某个循环索引之上；所有在共享张量之上的循环必须在相邻 PmappingGroup 之间完全匹配（co-tiled）；物理分布式存储之下的空间循环（数据绑定）也必须匹配。

图 10 · 两个 Einsum 的 join 示意（行数为假想值）。Compatibility 是 join 的"类型签名"：只有共享张量之上的循环结构完全一致的组才能配对。最优性来自每步保留带资源维度的完整 Pareto 前沿，而不是贪心取最好。

脏-净两阶段：先粗后精的容差阶梯

图 11 · 脏-净两阶段 join 的双层容差阶梯。外层对资源占用松绑，内层对目标值松绑；每层都是"先宽松求近似解 → 用近似解构造剪枝器 → 再精确求解"。这是论文"fast and optimal"中 fast 的第二个来源。

11. LoopTree 模型：复用分析、延迟与能耗

model/_looptree/ 的命名直接来自 LoopTree 论文。核心是 reuse/ 下的复用分析，有两个后端：symbolic/（sympy 闭式，默认且唯一被 run_model 调用）和 isl/（多面体精确分析，含 distributed/ 分布式存储绑定与 des.py）。timeloop_compare.rst 明确把 ISL 模型列为"Timeloop 有、AccelForge 进行中"，并说 AccelForge "使用更简单更快的解析模型"——所以 islpy 虽是硬依赖，主路径上只用它做负载层面的 rank 边界、张量大小等几何计算（frontend/_workload_isl/）。

图 12 · 模型内部四个阶段。延迟模型是 roofline 式的 max()：每个组件的忙时 = 动作数 / 吞吐，取最大者；没有排队、没有冲突。能耗 = 动作计数 × 单位能耗 + 漏电 × 时间，漏电按空间阵列实际占用比例做功耗门控折扣。

建模假设（assumptions.rst）在代码里的体现影响
每动作能耗恒定，与状态无关energy.py 直接 Σ count × energy无法建模 bank 冲突、地址相关功耗
内存由映射显式分配，即用即释Reservation 按 n_loops_above 分层累加无运行时分配器，无碎片
数据恰好准时到达，无双缓冲latency 不含等待项延迟偏乐观；真实设计需额外加 landing zone
每 Einsum 内延迟完美重叠，总延迟 = maxrun_model.py:78 max_nonzero(*latency.values())这是 Timeloop 的同款假设
目标随动作数单调增加§9 单调性剪枝的前提任何非单调成本项会让剪枝不安全
功耗门控：未用空间单元零功耗arch._power_gating对 CiM 这类大阵列影响显著

12. hwcomponents 集成与组件成本

AccelForge 自己不含任何电路级模型。Spec.calculate_component_costs()（spec.py:190）调用 hwcomponents.get_models(config.component_models) 拿到模型注册表，然后对架构树里每个 Component 叶子依次调 calculate_area / calculate_action_energy / calculate_action_throughput / calculate_action_latency / calculate_leak_power，把结果写回 Component.area、Action.energy 等字段，并按祖先 Spatialable 的扇出乘积算 total_area 与 total_leak_power。

component_class 决定模型

YAML 里 component_class: SmartBufferSRAM / LPDDR4 / IntMAC 对应 hwcomponents-library 里的类；CiM 示例用 hwcomponents-neurosim 的 RRAM/SRAM 阵列和 -adc 的 ADC 模型；-cacti 给 SRAM 面积功耗。

属性传递

extra_attributes_for_component_model（单组件）和 extra_attributes_for_all_component_models（全局，如 tech_node: 65e-9）原样传给模型构造函数；bits_per_action 把按比特计费换算成按动作。

手写优先

simple.yaml 完全不写 component_class，直接给 energy: 1 / throughput: inf——显式写的值优先，模型只填空缺。这让教学示例和真实技术节点建模用同一套 YAML。

一个工程细节：_clear_component_models()（spec.py:72）在并行前把 component_model 置空，因为 hwcomponents 模型对象可能包含动态加载的代码，无法 pickle。_memmap_read 把求值后的 spec 用 joblib memmap 共享给 worker。这些是把 Python 框架做到可并行所必须的"脏活"，也是论文宣称"Python 实现但高性能"背后的工程量。

14. 代码质量观察、局限与论文对照

值得借鉴的设计

  • 单一数据模型贯穿全程：frontend 的 Pydantic 对象从 YAML 解析一直活到模型输出，mapper 和 model 不做自己的中间表示。文档 timeloop_compare.rst 把这列为核心优势，代码证实了这一点。
  • 模型即单候选 mapper（§3）：消除了"手写映射的评估结果"与"mapper 找到的映射的评估结果"不一致的可能。
  • 用列名约定代替类型系统：df_convention.py 的 <SEP> 前缀分派让 Pareto、join、资源检查都能在 pandas 上向量化，而不用为每种列写对象。
  • 容差阶梯（§10）：以可控的近似换取数量级的速度，同时保留最终精确性。

观察到的问题

  • 调试残留：make_tile_shapes.py:62 有 DEBUG = getpass.getuser() == "tanner"；mapper/FFM/main.py:113 每次详细评估都把 mapping.svg 写到当前工作目录；同文件 :121–143 与 :155–159 有大段注释掉的调试代码；run_model.py:80–95 同样。
  • 目录名拼写：_make_pmappings/contraints/（应为 constraints），已被 import 路径固化。
  • Python 版本声明不准：requires-python >= 3.8，但代码用了 typing.Self（3.11）、enum.StrEnum（3.11）、X | Y 运行时联合（3.10）。
  • WIP 功能（文档自述）：稀疏、P2P 通信、layout 成本、模型侧 skew、ISL 高保真模型都未完成；Pipeline 节点存在但 make_pmappings.py:340 注释 "PIPELINE: This would have to change" 表明 join 尚不支持流水。
  • 测试覆盖不均：ISL 与网络有系统测试，但符号模型与 mapper 主路径的测试主要靠 notebook 执行（dev 依赖含 nbconvert）。

与论文概览稿的对照

论文说法代码实际
"Intra-Einsum mapper (TCM)" + "Inter-Einsum mapper (FFM)" 两个组件一个 mapper/FFM/ 包；intra 是 _make_pmappings/，inter 是 _join_pmappings/。没有 "TCM" 字样。
"fast mappers … orders of magnitude less time"来源有两处：符号模型按模板只跑一次 + 导数单调性剪枝（§9）；脏-净容差阶梯 join（§10）。论文未提及任何一处机制。
"optimal mapper"在假设成立（目标单调、因子化 tile、仅最外层余数）的前提下，Pareto 前沿逐步拼接是精确的；"optimal" 是相对于这个受限 mapspace 而言。
"Heterogeneous architectures"= 多条 FlattenedArch 路径 + Fork 节点，每条路径一组 Job（§5）。
"+Timing" 组件建模Action.throughput / latency 字段 + hwcomponents 的 throughput 模型；延迟 = 动作数 / 吞吐。
"Composable user-defined models of devices, circuits"全部外包给 hwcomponents；AccelForge 只传属性、收结果（§12）。
"Python implementations … high performance"靠 sympy/symengine + numpy lambdify + joblib + numba，以及把模型调用次数降到 O(模板数)。
和 Charon 对照：Charon 的后端对每个算子查表或预测一个数，前端做图变换；AccelForge 的后端对每个模板推导一个公式，前端做模板枚举。两者都把"搜索"与"成本"解耦，但 AccelForge 因为成本是闭式的，能把搜索的一部分（单调维度）用微积分直接解掉——这在 Charon 那种数据驱动的成本模型上做不到。反过来，Charon 能吃任意 PyTorch 算子，AccelForge 只能吃仿射索引的 Einsum。
