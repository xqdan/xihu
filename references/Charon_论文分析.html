1. 一句话结论与动机

训练 LLaMA-3 405B 要烧 1.6 万张 H100、超过 3000 万 GPU 小时；哪怕只在 GPU 型号、并行策略、并行度三个维度各给 4 个候选做穷举调优，总探索成本也能逼近 106 GPU 小时。Charon 的立场是：把 LLM 性能模拟当成一次编译器式的渐进变换——模型、调度、系统表示逐级细化，在速度、精度、可扩展性之间连续取舍，而不是在"分析式快但粗"和"profiling 准但慢"之间二选一。

3. 架构总览：前端 / 多引擎后端 / 设计探索器

Charon 吃两类输入：原生模型（HuggingFace / vLLM / 自定义 PyTorch）和系统配置（GPU/NPU 规格、互联拓扑、并行方案）。输出既有高层汇总（FLOPs、MFU、显存、功耗/TDP 估计），也有可选的细粒度执行 trace（PyTorch Profiler 风格的单层 timeline 和完整 3D 多卡 trace）。

图 1 · 原始输入经前端编译成带并行信息的计算图,交给多引擎后端做算子级模拟,最后由设计探索器在整个配置空间里剪枝搜索。

4. Graph-based 前端：原生模型直接吃进来

(a) 图生成

前端用 torch.fx.symbolic_trace 或 torch.compile 把原生模型转成中间计算图。因为现代 LLM 由大量重复的 Transformer block 堆叠而成，Charon 只抽取并模拟单个 decoder block，大幅加速模拟同时保留架构保真度；非对称模型或需要 PP 的场景则按模型定义把不同层追踪进独立 FX 图,按 rank 显式调度,保证跨 stage 依赖建模准确。为支持 disaggregated serving,prefill 和 decode 也可以被追踪成独立的计算图,分别映射到不同硬件集群。

训练任务需要反向图时，Graph Tracer 用 torch._functorch.aot_autograd 自动生成：给前向图加一个 dummy loss 和假输入张量以支持动态输出 shape，联合图（FWD+BWD）经过加元数据、重命名、去除 view/detach 等无用算子的多轮 pass 清洗后，用 default_partition 切成独立的前向/反向图模块，反向图再做自函数化算子分解、去自克隆、死代码消除。

图 2 · 前端图生成管线：原生模型经 torch.fx / torch.compile 追踪成 FX 计算图，推理路径直接取单个 decoder block 加速模拟；训练路径再经 aot_autograd 生成联合图并切分为独立的前向 / 反向图。

(b) 图优化与并行化 pass

优化和并行都被抽象成直接作用于计算图的 graph manipulation pass，加/删 pass 就能开关某个优化，不同 pass 可以自由组合成混合并行策略：

  • Shard 类（TP/SP/EP）：追踪计算图，调整分片算子的张量 shape，按选定策略在分片算子前后插入 all_reduce、all_gather、reduce_scatter。
  • PP：用 schedule pattern generator 构造跨设备的 stage 依赖，插入 send/recv 通信算子，支持经典 1F1B 调度和带计算通信重叠的 DualPipe 调度。
  • DP：支持 PyTorch DDP、FSDP、ZeRO。DDP 显式插入梯度同步的集合通信算子；FSDP/ZeRO 额外建模参数/优化器状态分片、状态同步与预取分析。

图 3 · 并行化与优化全部实现为作用在计算图上的 pass：Shard 类（TP/SP/EP）调整分片算子的张量 shape 并在前后插入集合通信；PP 用调度模式生成器构造 stage 依赖并插入 send/recv；DP 建模梯度同步与状态分片。所有 pass 可自由组合成混合并行策略。

算子重写和融合通过一套 match-and-replace 框架实现：遍历图找匹配预定义模式的节点，命中后修改节点类型和属性（合并多算子、替换低效算子形式）。新增优化规则只需定义新的匹配模式和变换动作，扩展性较好。量化既可以加一个精度变换 pass，也可以直接追踪已量化模型。

(c) 基于 pass 的多粒度分析

分析器统一用图处理同时支持两类指标：不依赖算子顺序的指标（如 MFU）直接在计算图上逐节点算，图遍历聚合成系统级结果；依赖执行顺序的指标（如详细 timeline）要调用后端拿每个算子的起止时间，再经 operator scheduler 根据算子间依赖（如 pipeline stage）精修出准确的执行 timeline。

内存建模是 Charon 区别于层级模拟器的关键点之一。层级模拟器只能按静态张量大小估算优化器状态和权重/梯度；Charon 利用反向计算图做张量生命周期（liveness）遍历，精确知道每个中间张量何时被分配、使用、释放，从而复现真实的临时张量复用和释放时机——这对评估 ZeRO、FSDP、选择性激活检查点这类"峰值显存出现在反向传播某个瞬间"的配置至关重要。

5. 多引擎后端：profiling / prediction / analytical / fused

后端负责模拟单个计算或通信算子的延迟，四种引擎各有取舍，统一支持 FP32/BF16/FP16/FP8/INT8 精度感知的延迟和显存建模。

引擎原理优点代价
Profiling Engine真机执行算子并计时，结果存进 profiling 数据库，命中（算子类型+shape）直接查表复用精度最高首次执行开销大
Prediction Engine每种算子类型配一个基于 profiling 数据训练的轻量 random-forest 预测器，从算子类型+输入 shape 直接估延迟覆盖 profiling 库里没见过的 shape，速度快依赖训练数据的代表性
Analytical Engine计算算子用 Roofline 模型（取计算时间和访存时间较大者）；通信算子用分层 link-centric 模型，拆解集合通信到物理链路级传输，按校准过的 per-hop 延迟和有效带宽算，支持 Ring/Tree 算法与 Ring/Switch/Mesh 拓扑不依赖 profiling 数据，覆盖新算子复杂算子（如 FlashAttention-3）误差大
Fused Engine按优先级 fallback：优先 profiling → 其次 prediction → 兜底 analytical，每种引擎维护自己支持的算子注册表新模型/新算子也能跑，不牺牲整体保真度-

图 4 · 后端引擎的优先级回退级联：profiling 精确但开销大，prediction 覆盖未见过的 shape，analytical 无数据也能算。三者按优先级 fallback，使新模型、新算子既能跑起来，又不拖累整体保真度。

通信分析的关键细节：Charon不依赖理论硬件规格，而是用从 profiling 校准出的 per-hop 延迟和有效带宽去建模集群拓扑，这样跨平台更可移植也更准。

6. 算子重叠建模：比例降速与带宽拥塞

现代训练/推理框架普遍把通信和计算、或通信和通信相互重叠。Charon 用两层模型描述重叠的代价：

粗粒度：比例降速模型

对所有重叠算子套用从目标集群 profiling 数据里标定的降速因子，只作用在两算子实际重叠的那一段。计算-通信重叠用两个独立降速因子；通信-通信重叠共享同一个降速因子。

细粒度：带宽感知拥塞模型

仅在 analytical 引擎下对通信-通信重叠生效。按每段重叠区间检查互联层级（NVLink / IB）的链路拥塞情况，根据有效带宽的竞争比例计算降速,逼近真实网络包级拥塞控制的效果。

图 5 · 论文 Figure 6 的带宽重分配示例：Comm Op0 单独跑时 NVLink 段满速 50 GB/s、IB 段 200 GB/s；与 Comm Op1 重叠后，Charon 按各自请求带宽的比例重新分配有效带宽（NVLink 降到 25 GB/s、IB 降到 160 GB/s），逼近真实网络包级拥塞控制的效果，而不是简单套一个固定折扣。

7. 设计空间探索：剪枝搜索

给定目标模型和任务，Charon 把用户输入的 GPU 数量、并行策略、并行度组合成完整设计空间，内置原生搜索工具，省掉"跑完模拟还要自己写脚本分析结果"这一层工程负担。用户可以预先标注已知的低效配置，搜索工具据此直接跳过对应子空间的模拟，提高搜索效率。这把"最优配置、期望性能、执行 timeline"三件事收口到同一次调用里。

图 6 · 设计空间探索把"用户输入的 GPU 数量 × 并行策略 × 并行度"铺成完整空间，先用规则剪掉用户标注的低效配置与明显越界项，再只对保留子空间调用多引擎后端，最终一次调用同时给出最优配置、期望性能和执行 timeline。

8. 实验：端到端精度、细粒度、内存、消融、跨规模

端到端精度（对比 Astra-SIM 2.0 / SimAI / Vidur）

测试模型覆盖两个稠密模型 Qwen3-8B、LLaMA3-8B 和一个 MoE 模型 Qwen3-30B-A3B。训练在 Megatron 和 VeOmni 框架下测，推理在 vLLM 框架下测。结果：Charon 在训练和推理任务、不同模型和框架组合下都拿到最佳端到端精度。

  • 对比 Astra-SIM：纯 analytical 建模通信/计算，粗粒度，Charon 的算子图级模拟明显更准。
  • 对比 SimAI：两者计算都走 profiling 后端，但 SimAI 的通信模拟继承自 Astra-SIM 1.0，是层级信息而非细粒度，处理通信重叠时会失真。
  • 对比 Vidur（推理）：两者 TTFT 都准（都是 profiling-based 计算+通信）；但 TPOT 上 Vidur 的 prediction 引擎对小算子精度不够，Charon 更稳。

内存预测精度

在 Qwen3-30B-A3B MoE 训练（8 GPU，FSDP=8，batch_size=2，seqlen=8192）上，最大已分配显存误差 +0.39%，最大保留显存误差 +0.29%，总显存误差 -0.03%——这得益于前面提到的基于 liveness 的图分析，而不是静态张量大小估算。

后端消融：analytical vs prediction

对未见过的 Linear、RMSNorm、FlashAttention-3 算子做统计偏差对比：analytical 引擎在 Linear（MAE 6.60%）、RMSNorm（MAE 5.70%）上尚可，但在 FlashAttention-3 上 MAE 高达 31.84%；prediction 引擎在三者上分别稳定在 1.44% / 1.12% / 2.22%。这组数字直接证明了"为什么需要混合引擎"——复杂 kernel 的解析模型会系统性失真，必须靠数据驱动的预测器兜底。

图 7 · 两个后端引擎在未见过的算子上的统计偏差（MAE）。解析模型在规整算子（Linear / RMSNorm）上尚可，但在 FlashAttention-3 这类复杂 kernel 上误差放大到 31.84%；预测引擎在三者上均稳定在 2.22% 以内 —— 这正是混合引擎存在的理由。

跨 GPU 架构与集群规模

覆盖 Nvidia Hopper/Ampere（H800/A100 训练）、Hopper/Ada Lovelace（H20/L20 推理），整体误差 <4.98%。集群规模从小到接近万卡（覆盖 DP/PP/EP/SP/TP 全并行组合），误差始终 <3.74%。两类误差的来源被归结为真实集群里网络抖动、动态拥塞、数据相关 kernel 执行的随机性——Charon 当前不对这些微观随机性做确定性建模，但不影响整体可靠性。

9. 案例研究：动态 SP 与推理 Pareto 前沿

9.1 动态 Sequence Parallel 策略

Zigzag attention（LLaMA-3 等大模型广泛使用）把序列维度切成 2×SP 块按 zigzag 模式分配给各 rank 以平衡负载，但对短序列并不划算——过度切分带来的 all-gather 通信开销会反超计算收益。论文用 Charon 分析不同序列长度分布下计算分布与通信开销的权衡，提出按请求动态选择 SP 配置：长序列继续用 zigzag 平衡，短序列降低切分避免多余 all-gather。

在 LLaMA-3 70B + 8× Ada Lovelace 推理 GPU 上验证，动态 SP 相对 zigzag 基线平均降低 attention block 延迟 15%，收益主要来自短序列请求省下的通信开销；作者预期在 PCIe 这类通信延迟更高的互联上收益会更大。

图 8 · 动态 SP 的核心权衡：zigzag 切分通过 2×SP 块平衡各 rank 负载，但对短序列而言多出的 all-gather 开销会反超收益。Charon 用分析结果支撑按请求长度切换 SP 配置，相对 zigzag 基线平均降低 attention block 延迟 15%。

9.2 推理性能的多目标优化

LLM 推理是 TTFT/TPOT（用户侧）与 TPS/GPU（硬件侧成本）的多目标优化，受调度算法、TP/PP 大小、prefill chunk size、prefill/decode batch size 等参数联合影响，解析求最优基本不可行，传统做法只能靠大量实测。

Charon 把这套搜索压缩到 2 分钟以内完成。在 LLaMA-3 70B + Hopper 推理 GPU 上扫描配置空间（图 13），找到的最优点（红点）相对次优配置在相同用户侧性能下明显更高的 TPS/GPU；沿最优前沿放松 TPS/user 约束，系统吞吐最多可提升 7×。在生产环境里，面对 100ms 端到端延迟 SLO 的固定输出长度服务，Charon 找到的配置明显优于工程师手调的基线。

图 9 · 推理配置空间的 Pareto 前沿（对应论文 Figure 13）。Charon 在 2 分钟内扫完 LLaMA-3 70B / Hopper 的完整配置空间，红点为找到的最优配置；灰色点是被支配的低效配置 —— 传统做法要靠大量实测才能分辨这两类点。

实现层面：Charon 依赖预先 profile 好的 kernel 延迟 + 多进程并行模拟来做到这个速度，并与自研推理框架和标准 HuggingFace Transformers 深度集成——自动从 HF 配置解析模型架构，从自研框架里提取 PyTorch FX 图和对应 kernel 实现，把使用门槛压到接近零。

10. 定位与局限

Charon 的核心方法论贡献是把"LLM 性能模拟"重新表述成一个编译器式的渐进细化问题：frontend 做图变换（trace→优化→并行→分析），backend 做算子级执行（可插拔的多引擎），顶层再叠一个设计空间搜索器。这个架构选择直接决定了它相对前序工作的四个优势——原生模型输入消除手搭/预处理成本、pass-based 设计让新优化和新并行策略"插拔"而不用重构核心、多粒度分析同时产出系统级指标和 PyTorch 风格细粒度 trace、混合引擎在速度和精度间做运行时取舍。

局限方面，论文自己承认的误差来源是不对真实集群的微观随机性做确定性建模（网络抖动、动态拥塞、数据相关的 kernel 执行随机性），这把精度天花板钉在个位数百分比而不是逼近 0。此外单 transformer block 抽取模拟是一个明确为对称架构设计的性能优化，非对称模型/异构 PP 需要退回到逐层追踪，工程复杂度更高。

与本仓库的关系：Charon 在硬件已定时搜索"怎么跑"（并行与调度），本仓库在负载已定时搜索"造什么芯片"（Core / SRAM / MC / NoC / RDMA）。本页只作方法参考，不是证据；借鉴方案（执行 trace 导出、链路级 τ 推导、重叠争用、算子成本提供者等）见 24 号建议稿。
