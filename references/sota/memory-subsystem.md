## 1. 一句话结论

公开资料里**不存在**「HBM/DRAM 控制器的 sustained 效率等于某个常数」这回事。存在的是**一层一层的分母**：
数据总线理论峰值（`data_rate × bus_width / 8`）是分母的起点，往下依次扣掉刷新占空、命令混合与读写转向、
bank/row 并行度不足、以及多主争用；每一层的折扣都是一个分布，而不是一个数。

公开可查的五个锚点，量级差了两个数量级：

- **顺序流式 + 无刷新**：可达 99.1%（HBM3 单通道复现实验口径，见 §3.3）。
- **顺序流式 + 刷新 + 厂商 achievable 口径**：约 **90%**（AMD/Xilinx 对 Alveo HBM2 的公开声明：460 GB/s 理论 / 420 GB/s achievable，见 SOTA-MEM-04）。
- **含刷新的理想流式、周期精确复现**：约 **92%**；**随机读**掉到约 **15–33%**；**单 bank 行冲突**掉到 **个位数百分比以内**（见 SOTA-MEM-07）。
- **真实大模型负载的 HBM 带宽饱和度**：厂商白皮书实测单请求 LLM 交互中 HBM 带宽占用最高到 **36%**；二手汇总口径给 AI 训练负载 **50–70%**（见 SOTA-MEM-14）。

把这四个锚点并列，含义是清楚的：**「MC 效率」这个系数若不绑定访问模式，它就不是一个物理量，而是一个把
「字节账错误 + 访问模式折减 + 协议开销 + 争用」打包在一起的混合系数。** 这与 `sustained-tps.md`
SOTA-TPS-10 对单因子折减的判断一致，本文件补的是它在内存侧的具体机理。本文件**不评价**本项目
`MC 效率 0.7` 这个取值落在哪一档——那需要先定死它绑定的是哪一种访问模式。

## 2. 方案分节

### 2.1 经典方案（上一代通行做法，用来判断「是不是落后了」）

**经典 A：把 raw 数据总线峰值当作效率分母，用「访问效率」一个数覆盖全部损耗。**
JEDEC 规范的峰值定义就是 `data_rate × bus_width / 8`，不含任何协议与器件开销。
上一代容量规划的做法是：拿峰值乘一个经验访问效率（工程手册常见的 70% 上下），
不再区分这个损耗来自刷新、行冲突还是读写转向（CSDN 技术博客，2025，作者原话大意是
「DRAM controller 能做到的访问 DRAM 的效率也顶多目前能做到 70% 上下」——
这是工程师经验口径，不是实测分布）。**这正是 `MC 效率 0.7` 这一档系数的来源形态**，
所以本项目在方法论上不属于落后；落后的风险在于不区分损耗来源时无法归因。

**经典 B：FR-FCFS + open page，目标最大化 row buffer hit rate。**
上一代 DRAM 控制器的默认调度：列命令（读/写）优先于行命令（ACT/PRE），行命中优先于先来先服务。
ETH/CMU 的体系结构课程把这条写成「调度实际发生在命令级，而不是请求级」——
即控制器先看哪些命令是 ready 的，再在 ready 的命令里按 raw-hit-first / oldest-first 排。
这条范式从 2000 年代沿用至今，Ramulator 系列模拟器（2015 CAL / 2023 arXiv 2.0）的默认配置就是它。
**知道这条的意义**：FR-FCFS 是吞吐优先的，它天然不保护尾延迟——这正是多租户干扰的来源（见经典/§2.2 的 QoS 部分）。

**经典 C：地址交错决定 bank 并行度，bank 并行度决定可达带宽。**
上一代通行做法是把连续物理地址轮流映射到 channel → bank group → bank → row，
使一个连续流式访问天然打散到全部 bank，从而隐藏 tRCD/tRP。
Xilinx 的 HBM 默认地址映射 `ROW BANK COLUMN BG0` 是公开可查的一条实例；
同一份文档明确指出：跨 4×4 交叉开关段会显著抬高时延，而每个连接的带宽是相同的，
所以「哪个 master 打到哪个 pseudochannel」直接决定有效带宽。
**判断「是否落后」的基准**：如果地址映射只做到「连续 8 MiB 对象顺序布局」而不控制
bank/row 的交错粒度，那它比公开通行做法更粗。

**经典 D：把内存当作单一资源池，不区分请求优先级。**
第一代 FPGA/ASIC 内存子系统没有 QoS 概念，所有请求 FIFO。代价在多主场景下被公开实测量化：
单 AXI master 打单 pseudochannel 可到 **约 95%** 利用率，64 个 master 同时发请求（地址不重叠）
掉到 **约 60%**（AMD 自适应计算社区帖，未标日期）。

### 2.2 SOTA 方案（近两代）

**SOTA A：把「可承诺 sustained」拆成一条三层折减链，并在每一层单独取证。**
这是近两代厂商文档的共同形态，而不是任何一个新硬件特性：

1. **口径层**：先声明分母是 raw 数据总线、还是协议可用 payload。NVIDIA 的工具把
   `pct_of_peak_sustained_elapsed` 明确对齐到「理论峰值按实际周期折算」，也就是**分母是 datasheet 峰值**，
   与实测达成率是两件事（NVIDIA Developer 论坛，2025）。Intel 的 HBM2 IP 则给出一条显式的效率公式，
   分母是 AXI 侧的有效事务数，且把「用户接口频率 / HBM 接口频率」的比值折进去——
   也就是说，**FPGA 这一派的效率口径里天然含一个时钟域比值项**，与 GPU 派的口径不可直接比。
2. **器件层**：扣刷新占空、扣温度档位。
3. **访问模式层**：按顺序/随机/混合给不同的达成率。

**SOTA B：刷新从「定时全 bank 刷」变成「可调度、可缩小范围」。**
DDR5 引入 Same-Bank Refresh（REFsb）与 Refresh Management（RFM，带 RAA 计数器）;
HBM3 用 REFpb（per-bank refresh）。控制器侧的对应做法是**机会式刷新**：
在写转向期间刷、在队列空闲时刷，甚至按刷新状态计数器的档位决定「忽略/写转向刷/双向刷」
（专利 US20200159463A1，2020）。**方向性结论**：刷新在近两代已经从「固定吃掉 x%」变成
「可被调度器挪走的开销」，所以它的实际代价取决于控制器实现，而不是规范常数。

**SOTA C：把 QoS 做成「槽位/信用分配 + 有界优先级」，而不是纯优先级或纯公平。**
公开的量化对照（FairDRAM，Ramulator 2.x 仿真，2025）：纯 FR-FCFS 下 CPU 侧慢 2.81×、
AI 侧吞吐损失 3.00%、Jain 公平指数 0.83；换成「默认走 FR-FCFS 行局部性、对紧急请求给有界优先级」后，
CPU 慢 1.93×、AI 吞吐损失升到 6.26%、公平指数 0.92。
**这是「QoS 要把吞吐让出多少」的一个可引用区间：给延迟敏感的请求让路，会让吞吐型负载损失
约 3% 抬到约 6%，全部实测 mix 下不超过 9%。**

**SOTA D：命令混合在链路层被显式重排。**
CXL 控制器的公开专利做法是在输入队列上开一个可伸缩的重排窗口，
把请求重排成「每 3 个请求 2 读 1 写」或「2 写 1 读」，让双向链路的两侧同时有 payload 跑，
从而提升带宽利用率、降低读延迟（专利 US20240320177A1，2024）。
**这条的物理前提是链路是双向且需要转向**；对半双工并行数据总线（HBM DQ），动机不同但转向代价同样存在。

**SOTA E：容量与带宽解耦，各买各的。**
HBM 这一代把两条轴彻底分开：带宽由 stack 数 × 接口宽度 × 引脚速率决定，
容量由堆叠层数（8-Hi / 12-Hi）与单 die 密度决定。HBM3E 的 8-Hi（24 GB）与 12-Hi（36 GB）
公开标称带宽同为 >1.2 TB/s；12-Hi 是把每片 die 磨薄约 40% 塞进同样的 720 µm 封装高度换来的容量，
**不带来带宽**（Micron HBM3E product brief，2023；AI Wiki HBM3e 汇总，2025）。
对「封装面积锁死内存颗数」的设计，这条的含义是：**加容量几乎不动 XY 面积，加带宽必须动岸线/bump**——
这两件事的物理成本完全不同，必须分开记账。

## 3. 各层折扣的公开取值

### 3.1 第一层：刷新占空比（tRFC / tREFI）

刷新期间 rank/bank 不可被访问，占空比就是 `tRFC / tREFI`。

| 口径 | 数值 | 条件 |
|---|---|---|
| DDR4（tRFC 350 ns / tREFI 7.8 µs，8K 次/64 ms） | **4.48%** | 常温；作者注「高温 tREFI 减半，会 suffer 10% 的效率 loss」 |
| DDR5 8 Gb（tRFC 195 ns / tREFI 3.9 µs，16K 次/64 ms） | **4.99%** | 常温；公开分析指出 DDR5 在纯 REFab 上并不优于 DDR4 |
| DDR5 16 Gb（tRFC 295 ns / tREFI 3.9 µs） | **7.56%** | 常温 |
| DDR5 16 Gb @ 85–95 °C（tREFI 减半到 1.95 µs） | **15.1%** | 高温档 |
| 跨代统计（DRAM 表征论文，2022） | 中位 **4.48%**（1 Kib 1.04% → 16 Kib 2.05% → 128 Mib 0.43% → 16 Gib 4.48%），DDR5 最坏 **7.56%** | 该统计明确指出**非单调**：容量涨、访问时间不涨，所以高密度器件反而更差 |

复现实验侧的对应量级：DDR4-2666 8 通道理论 170.6 GB/s，扣除全 bank 刷新后的「可达」上限
**164.2 GB/s**（≈96.2%），即刷新单独一项约 3.8 个百分点（arXiv 2510.15744，2025）。

**适用边界**：以上全是 DRAM 器件级的定时参数关系，与控制器调度无关；机会式刷新可以把这个
占空比在时间轴上调开，但**不能把总量消掉**。

### 3.2 第二层：命令混合与读写转向

| 来源 | 口径 | 数值 |
|---|---|---|
| HMC 链路效率随读/写比例（PhD thesis，UMD，2013） | 有效链路带宽 / raw 带宽 | 读占比 25% → **50.0%**；50% → **66.7%**；56% → **71.4%**（峰值）；66% → **60.0%**；75% → **53.3%** |
| 同上，定性结论 | — | 链路利用率「高度依赖读/写比例」，且**短时读/写比例**要匹配理想值；「66 读 + 34 写」的序列比「反复 2 读 1 写」的序列利用率低得多，尽管总比例相同。 |
| CXL 控制器重排窗口（专利，2024） | 操作化做法 | 重排成每 3 请求 2R1W 或 2W1R，让双向链路两侧同时载 payload |

**这是本文件里最容易被误用的一条。** 边界必须写清：该表是**分组化半双工串行链路（HMC）**的效率，
含包开销与转向惩罚；JEDEC 并行 DRAM 数据总线（DDR/LPDDR/HBM 的 DQ）是另一套物理，
其读/写代价通过**总线转向（tWTR/tRTW）与 write drain**体现，量级与形状都不同。
**不能拿 71.4% 当作 HBM 的读写混合效率。**

### 3.3 第三层：bank / row 并行度

这是三层里折扣最大的一层，也是「顺序 vs 随机」分野的来源。

| 场景 | 可达带宽（占该通道理论峰值） | 来源 |
|---|---|---|
| HBM3-6400 单 64-bit 通道，理想流式读、**关闭刷新** | 50.75 / 51.2 GB/s = **99.1%** | Ramulator2 复现实验 |
| HBM3-6400，流式读、**开启刷新** | 46.999 / 51.2 = **91.8%** | 同上（注意此文发布日可能晚于 `as_of`，见 §5「未解」） |
| HBM3-6400，随机读、开启刷新 | 15.419 / 51.2 = **30.1%** | 同上 |
| HBM3-6400，单 bank 行冲突（读队列限 1，防调度器重排成行命中） | 0.665 / 51.2 = **1.3%** | 同上 |
| Alveo U280 单 pseudochannel，顺序访问 | 读 13.0 / 写 13.1 / 读写 12.9 GB/s（ideal 14.4）→ **≈90%** | FPGA 会议论文，2021 |
| 同板，**交错访问多个数组** vs 顺序访问 | 交错 < **10%**（DRAM row buffer thrashing） | SFU 硕士论文微基准，2024 |
| 多主争用：1 master 打 1 PC | **≈95%** | AMD 社区帖（未标日期） |
| 多主争用：64 master 同时打（地址不重叠） | 掉到 **≈60%** | 同上 |

**读法**：同一颗 HBM、同一个控制器，只换访问模式，可达带宽从 99% 掉到 1.3%。
所以「MC 效率」的任何单一取值，其含义完全由它绑定的访问模式决定。
公开资料里**没有**找到「给定一个 mixed 工作负载，控制器平均达成多少」的通用分布——
见 §5。

### 3.4 第四层：温度与热降额

- DDR5 的 tREFI 在 85–95 °C 档位**减半**，刷新占空比随之翻倍（器件数据表，见 3.1）。
- Intel HBM2 IP 文档把 temperature 列为「减少可用于数据传输的带宽」的两大因素之一，
  并暴露一个可配置的 `AXI throttling ratio` 参数——即**厂商把热降额做成一个显式的带宽乘数**，
  而不是隐含项（Intel FPGA 文档，2020）。
- 厂商口径的温度鲁棒性声明（第三方汇总）：某厂商声称其 HBM3E 在 105 °C 仍保持 92% 峰值带宽，
  竞品衰减到 85% 以下（CSDN 二手汇总，日期 UNVERIFIED）。**这条来源质量低，仅作方向参考，
  不作为数值依据。**

### 3.5 第五层：真实大模型负载的 HBM 带宽饱和度

| 口径 | 数值 | 条件 |
|---|---|---|
| Micron 白皮书（2025） | LLM 交互期间 HBM 带宽占用**最高到 36%**；batch 从 100 增到 1K 时利用率**升 1.37×**、增到 10K 升 **1.45×** | 192 GB HBM3E + 2 TB DDR5，agentic workflow，单请求到高并发 |
| 中文技术汇总（未标日期） | HBM3 实际可持续带宽「通常只有峰值的 **70–85%**」；大多数 AI 训练负载 HBM 带宽饱和度 **50–70%**，优化数据布局后可 **80%+** | **二手汇总、无一手测量出处，本文件只作区间参考，不作依据** |
| 厂商营销口径 | H200（HBM3E 4.8 TB/s）相对 H100（HBM3 3.35 TB/s）在 Llama2-70B 上带宽单独贡献 **1.2×** 吞吐 | Micron HBM3E H200 technical brief，2024 |

## 4. 「从 datasheet peak 推出可承诺 sustained」——行业通行做法

把公开资料里能找到的做法归纳成一条链，**每一环都要求单独取证**，而不是末端乘一个系数：

1. **定分母**：写清峰值是 `data_rate × bus_width / 8`（raw 总线），还是协议层可用 payload。
   Intel 的 HBM IP 效率公式里含一个「用户时钟 × 2 / HBM 接口频率」项，
   NVIDIA 的 `pct_of_peak` 对齐 datasheet 峰值——**两家的分母定义不同，不可互引**。
2. **扣器件固定开销**：刷新占空（常温 4–8%，高温档翻倍）、refresh management 的额外命令、
   训练/校准（link training）窗口。
3. **扣协议与重传开销**：ECC/CRC、retry、lane repair —— 这一环本文件**没有找到可引用的
   百分比区间**（见 §5）。
4. **按访问模式给达成率**：顺序流式 ≈90%（厂商公开 achievable 口径）起，随机读掉到 15–33%，
   行冲突最坏 <5%。
5. **扣热降额**：把温度档位下的 tREFI 变化与厂商的 throttling ratio 显式乘进去。
6. **扣多主/QoS 让路**：给延迟敏感流让路会让吞吐型负载损失约 3%→6%（不超过 9%）。
7. **反推验证**：用「每 token 实际搬运字节 ÷ 实测时延」得达成 GB/s，再与**同机 STREAM/BabelStream
   ceiling** 比——这套方法论 `sustained-tps.md` SOTA-TPS-09 已给出，本文件不重复，
   只提醒一点：**分母必须用聚合 ceiling**，用单通道 ceiling 会算出 >100% 的无意义利用率。

**行业上没有出现「一个通行的 peak→sustained 折减系数」**。这一点本身是结论性的：
公开资料给的是**一条随访问模式从 ~90% 滑到 <5% 的曲线**，而不是一个标量。

## 5. 明确查不到的部分（不要用相邻领域数字凑）

1. **MC 控制器在真实 mixed 工作负载下的达成率分布**——没有。公开资料给的是**合成 trace**
   （stream_read / random_read / row_conflict / mixed_70r30w 这类）在开源模拟器上的曲线，
   而不是「某个真实推理负载跑在某颗 HBM 上，控制器达成率是多少」的分布。
   与本项目对得上的那类参照系（长上下文 decode 的访问模式 + 656 B 粒度 gather）
   在公开资料里**完全缺失**。
2. **ECC / CRC / retry / lane repair 的实际带宽开销百分比**——没有找到可引用的公开区间。
   本项目 `04_MEMORY_SUBSYSTEM_MC.md` 第 8 节把「UCIe replay/ECC 开启后的 payload」
   列为必核项，公开资料帮不上，只能向供应商要。
3. **外挂式 Memory Cube（logic die + DRAM 堆叠 + UCIe 挂在 compute die 外）这一类器件的
   sustained 效率实测**——没有。公开可查的 HBM 数据全部来自「compute die + HBM stack 同封装中介层」
   这一形态；本项目的参考器件（UCIe 1.1、8 条 UCIe、320 GB/s 单向）属于另一类封装形态，
   **没有可类比的公开折减曲线**。这是一个明确的空白，不是本文件检索不力。
4. **多颗内存器件同时工作时的热降额曲线**——没有公开的「8/16 颗同时满带宽时的降额百分比」。
   厂商给的是单器件温度-降额关系，不是器件数-降额关系。
5. **zhihu 上的一份 Ramulator2 v2.1.0 复现实验**给出了本文件 §3.3 里最完整的一组 HBM3 分场景数字
   （99.1% 无刷新流式、91.8% 含刷新流式、30.1% 随机读、1.3% 单 bank 行冲突、REFpb 相对 REFab 变化）。
   该文的发布日期**无法确认是否早于 `as_of`（2026-01）**，且其 REFpb/REFab 对照结论明确自称
   「只适用于该版本严格 round-robin 的实现与本文固定 trace」。**本文件引用其量级（作为
   「访问模式支配可达带宽」这一结论的实例），但不把其中的具体百分比当作跨实现的普适常数。**
   下一轮刷新时若该文仍在，应补核其发布日期。
6. **同一批检索里出现的若干 2026 年 9 月的 arXiv 预印本**（FPGA HBM profiling 框架、
   HBM+flash 分层 KV 等）**已被排除**，因为发布日在 `as_of` 之后。这解释了为什么
   「近存/分层存储」这一节在本文件中只有方向性描述而没有数字。
7. **`WebSearch` 工具在本轮多次调用中返回分类器/参数错误（`***.***.disabled`）而失败**；
   成功的检索全部通过运行时 `web_search` 取得。未因工具失败而编造任何一条来源。
