# Pipelines

Reproducible entry points for the final tuning search, the planning pipeline and report generation. Every script resolves paths from the repository root (it `chdir`s there or joins onto it), so it can be run from any directory. Generated outputs go to `out/`; the only exception is `sync_baseline_spec.js`, which rewrites the model-derived fields of `teams/hardware/inputs/k3_mc_baseline.json` (see `teams/hardware/README.md`).

Planning pipeline (in this order after a model change):

```sh
npm run search:final        # run_search.js final -> out/rdma/k3_rdma_final_tuning_results.json
npm run baseline:sync       # sync_baseline_spec.js -> teams/hardware/inputs/k3_mc_baseline.json, out/direction/directional_workload_baseline.json
npm run aicore:search       # generate_matrix_vector_design.js -> out/detailed/matrix_vector_design.json + matrix_vector_candidates.json
npm run commcore:search     # generate_comm_core_design.js -> out/detailed/comm_core_design.json + comm_candidates.json
npm run memory:search       # generate_memory_design.js -> out/detailed/memory_design.json + memory_candidates.json
npm run sram:search         # generate_sram_design.js -> out/detailed/sram_design.json + sram_candidates.json
npm run physical:search     # generate_physical_design.js -> out/detailed/physical_design.json + physical_candidates.json
npm run coupling:search     # generate_coupling_design.js -> out/detailed/coupling_design.json + coupling_candidates.json (reads the five domain designs above)
npm run model:planning      # generate_planning_operator_workload -> stage_a -> stage_b -> generate_team_contracts -> generate_direction_feedback -> generate_global_dashboard
npm test
```

- Reproducibility: generated artifacts carry no wall-clock time, and `tests/governance/test_regeneration_reproducible.js` reruns the six `*:search` scripts and `model:planning` in a scratch copy and requires `out/` to match byte for byte. The only environment input is `K3_SOURCE_COMMIT` (read by `stage_a.js` / `stage_b.js`), which pins the provenance commit for that comparison; leave it unset for a real run. After any change to a generator or its inputs, rerun the pipelines and commit `out/` together with the change, or this test fails. `search:final` and `baseline:sync` are not part of that rerun.
- `run_workflow.js` (`npm run workflow:run -- <workflow> --backend mock|claude|cursor|exchange [--land] [--result-file f]`): the main loop for a `design.*.workflow.js` outside Claude Code. It injects the workflow globals (`integration/orchestration/runtime/`), prepares `args.searchBrief` for the C group (and the sensitivity card for `attribution`, the budget frontier for `req.budget`, each refused when built from other inputs — a card also when built at another design point — and `args.designPoint` for `converge`), derives `args.brief` for the budget contract's consumers (`make_brief.js`) and injects `args.ledger` (`design_ledger.js`), snapshots the working tree to prove agents stayed read-only, checks a C-group winner against the candidate artifact (and a `req.budget` contract against its frontier split, `verifyLandedBudget`), then lands the returned files through path and content gates and merges the workflow's `ledgerPatch` back into the ledger. A run that returns no files (a backflow, a blocked input) lands an outcome record instead. Without `--land` it is a dry run — the ledger included. See `integration/orchestration/README.md`.
- `make_brief.js` (`npm run workflow:design-brief -- <stage> [--contract f] [--split S-CMP] [--provenance]`, `-- --list`): builds one stage's `DesignBrief` instead of letting an architect retype it. The prose (objective, shape intent, `forbidden`, `exitCriteria`, allowed design space, profile binding) comes from `teams/council/inputs/brief_intents.json`; every number — the area / power / bandwidth budget and seven hard constraints — is derived from a budget contract, each carrying a JSON-Pointer `source` into the split entry it came from, so the brief holds no second copy of a contract number. Covers the contract's consumers: `direction`, `compute`, `sram`, `mc`, `comm`, `physical`, `coupling`. The contract is the first of `--contract <file>`, `out/budget/L1_budget.json`, a split of `out/requirements/budget_frontier.json` (default `S-CMP`), or — stage `compute` only — the committed `design_brief.m2.json`. The built brief is validated against `design_brief.schema.json` before it is handed over, and it is never stored: a stored copy is what goes stale. `profileBinding.mcProfile` is deliberately hand-authored rather than read off the contract's point, because ADR-0021 makes MC320 the sole manufacturable default and MC640 a stretch tier.
- `design_ledger.js` (`npm run workflow:ledger`, `npm run workflow:ledger-check`): the `DesignLedger` at `out/governance/design_ledger.json` — the only thing that crosses a stage boundary. Every workflow returns a `ledgerPatch` (`design.intake` a whole `ledgerSeed`); the main loop merges it back after a successful `--land`. Merge rules: `currentStage` overwritten, `strategyVersions` and `budgetBalance` merged per key, `rejectedOptions` / `openBlockers` / `evidenceIndex` merged by natural key and never dropped (an option that was ruled out must not be reinvented by a re-run, and a blocker nobody mentioned is not a resolved blocker), and a patch that gives a frozen decision a different text is an error rather than a merge. The merged ledger is validated against `design_ledger.schema.json` before it is written. It does not go through `land.js`: `out/governance/` is a landing prefix for `dgate` and `backflow`, and the ledger is the loop's own record, not a workflow output.
- `search_brief.js` (`npm run workflow:brief -- <stage>` / `npm run workflow:verify-landed -- <stage>`): the deterministic half of the C-group design workflows and of `design.coupling` (`STAGES`: the five domains plus `coupling`). `brief` reads `out/detailed/<stage>_candidates.json`, checks that it was searched over the design space on disk and that a fresh search reproduces its `candidateSetSha256`, and prints the `searchBrief` (ranked head, verbatim rows) that the main loop passes as `args.searchBrief`. `verify` runs after a workflow's files land and checks that the landed winner (`out/<domain>/<domain>_winner.json`; for coupling `out/coupling/joint_point.json`, see `landedFiles()`) is a verbatim, feasible row of that artifact, that any field it carries beyond the row (the joint point's `x` / `opt` / `model`) equals the row's own, and that the run record names the same fingerprint.
- `design_point.js` (`npm run workflow:design-point [-- --point auto|joint|published]`): the one design point the stages downstream of `design.coupling` work on. `auto` is the landed joint point (`out/coupling/joint_point.json`) if there is one, else the published point of the baseline; a landed joint point is first checked with `search_brief.js verify` and a joint point that does not verify is an error, never a silent fall-back to the published one. It returns the point's `x` / `opt` / `model`, a `sha256` over them (the identity a sensitivity card records in `inputs.point` and `run_workflow.js` compares) and its `departures` from the baseline (`x.*`, `opt.*`, `model.*`). `generate_tps_attribution.js` (`npm run attribution:cards`, same `--point` flag) builds the L4 cards at that point, replayed through `coupling_search.withPoint`; `design.converge` gets it as `args.designPoint` and blocks when it departs from the baseline, because the D-group artifacts were computed by `stage_b.js` at the baseline — moving the baseline takes an ADR and `baseline:sync`.
- `generate_budget_frontier.js` (`npm run budget:frontier`): writes `out/requirements/budget_frontier.json` from `integration/planning/requirement_frontier.js` (doc 23 L1-b). On planning token time it gives, per model × TP, the bandwidth floor (the memory lane exactly on the raw budget) and the compute ↔ τ iso-TPS line; on the K3 TP32 detailed model it gives the single-axis room for τ, compute scale and MC payload and the smallest shared SRAM that holds; then it builds four candidate budget contracts (`S-TAU`, `S-CMP`, `S-BW`, `S-BAL`), each rechecked under both models at its own point. The die area limit is the one the detailed model enforces (`k3_physical_basis.BASIS.limits`). Reads the baseline and `out/workload/planning_operator_workload.json` and records their sha256, so run it after `model:planning`; `tests/regression/test_budget_frontier.js` requires the stored file to equal a rebuild. A build takes about 20 s.
- `generate_planning_operator_workload.js`: K3 operator FLOP/byte rows derived from `teams/model/src/design_engine.js` (single K3 shape source, FP8 KV 656 B/token/layer) and reconciled with the detailed plan; GLM-5.2 and DeepSeek-V4-Pro rows come from the Model team derivation `teams/model/src/workload_derivation.js` (manifest `shape` plus explicit ASSUMPTION fields, MTP excluded, ADR-0007). It also fits the planning token-time calibration on the K3 detailed published point and checks it at MC320 (ADR-0008).
- `stage_a.js`: Stage A direction comparison. The resource envelope comes from `integration/planning/directional_envelope.js`; the D-Gate is computed by `integration/governance/evaluate_gates.js`. It also writes the L2 morphology space (doc 23 L2, `integration/planning/morphology.js`): the published point with its coarse shape moved one axis at a time (L/H core ratio, on-chip SRAM total and its local/shared split, MC tier, die count, TP), each shape scored for area/power through `k3_architecture_search.physical(x, dies)` rescaled by `k3_physical_basis.resize()` and for TPS through `token_time.js`, then checked entry by entry against the L1 contract's `S-CMP` split. The shapes ride in the scorecard's own `morphology` block and never in `resourceProfiles`, and the D-Gate still reads only the 18-row candidate grid. Writes `out/budget/L2_budget.json` — the L1 entries with `B-SRAM-CAP` refined into local and shared per die, everything else inherited verbatim. Run it after `budget:frontier`: the morphology table is measured against that contract.
- `stage_b.js`: Stage B planning quantification of the selected candidates.
- `integration/planning/token_time.js` (used by Stage A and B): `raw = max(kMemory × (memory + expertReread × routed-expert memory), kFlop × compute + fixed per layer + exposed TMA + collectives × τ)`, `e2e = raw × 1.17`; every slot also reports τ = 1.15 / 1.5 / 2.0 µs (ADR-0008).
- `generate_team_contracts.js`: merges `teams/<team>/contract.json` with the current artifacts into `out/contracts/`, and writes the integration manifest with contract hashes.
- `generate_direction_feedback.js`: Stage B -> Stage A backflow (`out/governance/direction_feedback.json`, open blockers and best planning estimate per model).
- `generate_global_dashboard.js`: `out/dashboard/architecture_global_dashboard.html`; reads the blockers from the feedback file, so run it after `generate_direction_feedback.js` (`npm run dashboard` runs both).
- `run_search.js final`: runs the final tuning search (`integration/detailed/k3_rdma_final_tuning_search.js`), the source of the published point; it also writes `out/rdma/k3_rdma_final_tuning_report.html`. The candidate evaluations run on a pool of worker threads (`integration/detailed/eval_pool.js`): about 19 s on 8 jobs against about 77 s on one, the same result row for row. `K3_SEARCH_JOBS=N` sets the job count (default: logical cores less one, at most 8; `1` evaluates in the calling thread). The visiting order, row ids and random stream are those of the serial search, which `tests/regression/test_final_search_parallel.js` checks against a verbatim copy of it.
- `sync_baseline_spec.js` (`npm run baseline:sync [-- --point published|joint --adr <file>]`): rewrites only the model-derived fields of the machine-readable P1 baseline so numbers are never hand-copied. `--point published` (the default) takes them from the Final Tuning search best at the model's own OPT and model. `--point joint --adr <file under teams/council/adr/>` takes them from the landed joint point (`out/coupling/joint_point.json`, resolved and verified by `design_point.js`) instead: every field is replayed inside `coupling_search.withPoint` with the point's OPT and model patch, the die area counts the option overheads and the Comm Core, and the baseline records the point in a `designPoint` block — after which `design_point.js` reports no departures and `design.converge` stops blocking on it. The ADR must cite the point's `optionId` and sha256, because moving the baseline is a decision rather than a side effect of a landed file. `build()` does the work without writing, so a test can run it at an injected point. `integration/detailed/baseline_point.js` then stops the modules that replay `tpsDesign.hardware.x` without the patch.
- `generate_matrix_vector_design.js`: AI Core matrix:vector design search (HW-02, `teams/hardware/docs/02_AI_CORE.md` section 2.5) over the design space `teams/hardware/inputs/matrix_vector_design_space.json` (vector lanes, vector unpack or native FP8/MXFP4 tensor input, exp SFU or polynomial): scores every combination on the per-kernel hiding bounds of K3, GLM-5.2 and DeepSeek-V4-Pro and on a K3 detailed replay, keeps candidates that hide every H-core kernel, keep the published TPS/usr within 0.1% and fit the die, and ranks them by area (with the option overheads) and power. Writes the winner to `out/detailed/matrix_vector_design.json` — which deliberately holds no candidate list, because the design document quotes that file and the alternatives stay in the design space — and the whole scored candidate set, with a reproducible `candidateSetSha256` fingerprint over it, to `out/detailed/matrix_vector_candidates.json`. That second file is what a consumer which merges, ranks or excludes candidates is checked against: a winner-only artifact cannot support "every exclusion is traceable", since the excluded entries were never written down. Prints the per-option comparison and the analysis tables for the document. Reads the published point from the baseline, so run it after `baseline:sync`.
- `generate_comm_core_design.js`: Comm Core design search (HW-07, `teams/hardware/docs/10_COMM_CORE.md` section 7) over the design space `teams/hardware/inputs/comm_core_design_space.json`: enumerates every combination of the searched dimensions, adds each candidate's control path (trigger, graph fetch, WQE dispatch, doorbell, completion) to every collective class, keeps candidates within the spec tau, the SRAM capacity and the utilization limit, and ranks them by AI Core time, spec slack and area. Writes only the winner to `out/detailed/comm_core_design.json` and prints the best candidate of every option for the document. The ranked candidate head goes to `out/detailed/comm_candidates.json`, which is what `design.comm` reads: a winner-only artifact cannot support "every exclusion is traceable". This grid enumerates 216000 combinations and scores 45900 where the siblings score hundreds, so that file is the one place in this repository where the listing is knowingly truncated (`listed` / `truncated`) — the `candidateSetSha256` fingerprint is taken over the whole scored set and `infeasibleByCause` counts every excluded candidate by its violation set, so neither "these are the candidates that were searched" nor "why was X dropped" depends on the listing. Reads the published point from the baseline, so run it after `baseline:sync`.
- `generate_memory_design.js`: MC / Memory Cube design search (HW-04, `teams/hardware/docs/04_MEMORY_SUBSYSTEM_MC.md` section 5.1) over the design space `teams/hardware/inputs/memory_design_space.json` (MC tier, cubes per card, capacity per cube, bandwidth route, ECC overhead): scores every combination on a K3 detailed replay, keeps candidates that hold the published TPS/usr within tolerance and clear the program goal, the package placement window, the die area limit and this domain's card power caliber — where the card power is `8 x die + MC + the fixed 80 W` and deliberately does NOT charge the shared-port term the physical domain adds, so 2800 W is a looser check here by exactly 21.915648 W — and ranks them feasible-first, then by manufacturing risk class, then card-level MC power. Writes the winner to `out/detailed/memory_design.json` (no candidate list: the design document quotes that file and the alternatives stay in the design space) and the whole scored candidate set, with a reproducible `candidateSetSha256`, to `out/detailed/memory_candidates.json`. A route the search did not model is excluded by violation, not left to lose a tie-break on price. Reads the published point from the baseline, so run it after `baseline:sync`.
- `generate_sram_design.js`: SRAM / TMA design search (HW-03, `teams/hardware/docs/03_TMA_AND_SRAM.md` section 8) over the design space `teams/hardware/inputs/sram_design_space.json` (shared window per die, L/H local bank counts, shared slices, TMA engines per core, shared-port scaling on/off): tests the L1 contract entry `B-SRAM-CAP` directly on the window (a candidate below it is not replayed), replays K3 at the published point with only those dimensions changed against the contract `target.tpsPerUser`, holds the die to `B-AREA`'s area and power limits with the shared-port charge included, and ranks feasible candidates by die area then die power. Writes the winner to `out/detailed/sram_design.json` and the whole scored set with `candidateSetSha256` and `infeasibleByCause` to `out/detailed/sram_candidates.json`; prints the per-option table, the `B-SRAM-CAP` sweep, the local-capacity sweep and the published combination's rank for the document. Checked by `tests/regression/test_sram_design.js`.
- `generate_physical_design.js`: Package / power / RAS design search (HW-09, `teams/hardware/docs/09_PACKAGE_POWER_RAS.md` section 3) over the design space `teams/hardware/inputs/physical_design_space.json` (process, matrix density, cooling, keep-out fraction): enumerates every combination, checks area conservation (`placed + keep-out <= 5248 mm²`, tolerance 0), the die area and power limits, the package placement window, the PHY shoreline and a K3 detailed replay, and ranks them feasible-first, then by the most conservative keep-out premise, then the largest reserve within that premise, then die power margin, then process risk. The keep-out is the share of the window that is LEFT OUT (published 0.1254 = 658.29/5248), not a usable share — reading it backwards inverts every area number. The most conservative premise outranks the largest reserve on purpose: 0.10 is numerically feasible but asserts a smaller keep-out than anything in the repository supports. Writes the winner to `out/detailed/physical_design.json` and the whole scored candidate set, with a `candidateSetSha256`, to `out/detailed/physical_candidates.json`. Reads the published point from the baseline, so run it after `baseline:sync`.
- `models/detailed_run.js` and `models/direction/run_directional_tps.js` were retired and deleted (ADR-0006); use `npm run model:planning`.
