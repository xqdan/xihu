# Pipelines

Reproducible entry points for the final tuning search, the planning pipeline and report generation. Every script resolves paths from the repository root (it `chdir`s there or joins onto it), so it can be run from any directory. Generated outputs go to `out/`; the only exception is `sync_baseline_spec.js`, which rewrites the model-derived fields of `teams/hardware/inputs/k3_mc_baseline.json` (see `teams/hardware/README.md`).

Planning pipeline (in this order after a model change):

```sh
npm run search:final        # run_search.js final -> out/rdma/k3_rdma_final_tuning_results.json
npm run baseline:sync       # sync_baseline_spec.js -> teams/hardware/inputs/k3_mc_baseline.json, out/direction/directional_workload_baseline.json
npm run aicore:search       # generate_matrix_vector_design.js -> out/detailed/matrix_vector_design.json + matrix_vector_candidates.json
npm run commcore:search     # generate_comm_core_design.js -> out/detailed/comm_core_design.json + comm_candidates.json
npm run memory:search       # generate_memory_design.js -> out/detailed/memory_design.json + memory_candidates.json
npm run physical:search     # generate_physical_design.js -> out/detailed/physical_design.json + physical_candidates.json
npm run model:planning      # generate_planning_operator_workload -> stage_a -> stage_b -> generate_team_contracts -> generate_direction_feedback -> generate_global_dashboard
npm test
```

- Reproducibility: generated artifacts carry no wall-clock time, and `tests/governance/test_regeneration_reproducible.js` reruns the four `*:search` scripts and `model:planning` in a scratch copy and requires `out/` to match byte for byte. The only environment input is `K3_SOURCE_COMMIT` (read by `stage_a.js` / `stage_b.js`), which pins the provenance commit for that comparison; leave it unset for a real run. After any change to a generator or its inputs, rerun the pipelines and commit `out/` together with the change, or this test fails. `search:final` and `baseline:sync` are not part of that rerun.
- `run_workflow.js` (`npm run workflow:run -- <workflow> --backend mock|claude|cursor|exchange [--land] [--result-file f]`): the main loop for a `design.*.workflow.js` outside Claude Code. It injects the workflow globals (`integration/orchestration/runtime/`), prepares `args.searchBrief` for the C group (and the sensitivity card for `attribution`, the budget frontier for `req.budget`, each refused when built from other inputs), snapshots the working tree to prove agents stayed read-only, checks a C-group winner against the candidate artifact (and a `req.budget` contract against its frontier split, `verifyLandedBudget`), then lands the returned files through path and content gates. A run that returns no files (a backflow, a blocked input) lands an outcome record instead. Without `--land` it is a dry run. See `integration/orchestration/README.md`.
- `search_brief.js` (`npm run workflow:brief -- <domain>` / `npm run workflow:verify-landed -- <domain>`): the deterministic half of the C-group design workflows. `brief` reads `out/detailed/<domain>_candidates.json`, checks that it was searched over the design space on disk and that a fresh search reproduces its `candidateSetSha256`, and prints the `searchBrief` (ranked head, verbatim rows) that the main loop passes as `args.searchBrief`. `verify` runs after a workflow's files land and checks that `out/<domain>/<domain>_winner.json` is a verbatim, feasible row of that artifact and that the run record names the same fingerprint.
- `generate_budget_frontier.js` (`npm run budget:frontier`): writes `out/requirements/budget_frontier.json` from `integration/planning/requirement_frontier.js` (doc 23 L1-b). On planning token time it gives, per model × TP, the bandwidth floor (the memory lane exactly on the raw budget) and the compute ↔ τ iso-TPS line; on the K3 TP32 detailed model it gives the single-axis room for τ, compute scale and MC payload and the smallest shared SRAM that holds; then it builds four candidate budget contracts (`S-TAU`, `S-CMP`, `S-BW`, `S-BAL`), each rechecked under both models at its own point. The die area limit is the one the detailed model enforces (`k3_physical_basis.BASIS.limits`). Reads the baseline and `out/workload/planning_operator_workload.json` and records their sha256, so run it after `model:planning`; `tests/regression/test_budget_frontier.js` requires the stored file to equal a rebuild. A build takes about 20 s.
- `generate_planning_operator_workload.js`: K3 operator FLOP/byte rows derived from `teams/model/src/design_engine.js` (single K3 shape source, FP8 KV 656 B/token/layer) and reconciled with the detailed plan; GLM-5.2 and DeepSeek-V4-Pro rows come from the Model team derivation `teams/model/src/workload_derivation.js` (manifest `shape` plus explicit ASSUMPTION fields, MTP excluded, ADR-0007). It also fits the planning token-time calibration on the K3 detailed published point and checks it at MC320 (ADR-0008).
- `stage_a.js`: Stage A direction comparison. The resource envelope comes from `integration/planning/directional_envelope.js`; the D-Gate is computed by `integration/governance/evaluate_gates.js`.
- `stage_b.js`: Stage B planning quantification of the selected candidates.
- `integration/planning/token_time.js` (used by Stage A and B): `raw = max(kMemory × (memory + expertReread × routed-expert memory), kFlop × compute + fixed per layer + exposed TMA + collectives × τ)`, `e2e = raw × 1.17`; every slot also reports τ = 1.15 / 1.5 / 2.0 µs (ADR-0008).
- `generate_team_contracts.js`: merges `teams/<team>/contract.json` with the current artifacts into `out/contracts/`, and writes the integration manifest with contract hashes.
- `generate_direction_feedback.js`: Stage B -> Stage A backflow (`out/governance/direction_feedback.json`, open blockers and best planning estimate per model).
- `generate_global_dashboard.js`: `out/dashboard/architecture_global_dashboard.html`; reads the blockers from the feedback file, so run it after `generate_direction_feedback.js` (`npm run dashboard` runs both).
- `run_search.js final`: runs the final tuning search (`integration/detailed/k3_rdma_final_tuning_search.js`), the source of the published point; it also writes `out/rdma/k3_rdma_final_tuning_report.html`.
- `sync_baseline_spec.js`: rewrites only the model-derived fields of the machine-readable P1 baseline so numbers are never hand-copied.
- `generate_matrix_vector_design.js`: AI Core matrix:vector design search (HW-02, `teams/hardware/docs/02_AI_CORE.md` section 2.5) over the design space `teams/hardware/inputs/matrix_vector_design_space.json` (vector lanes, vector unpack or native FP8/MXFP4 tensor input, exp SFU or polynomial): scores every combination on the per-kernel hiding bounds of K3, GLM-5.2 and DeepSeek-V4-Pro and on a K3 detailed replay, keeps candidates that hide every H-core kernel, keep the published TPS/usr within 0.1% and fit the die, and ranks them by area (with the option overheads) and power. Writes the winner to `out/detailed/matrix_vector_design.json` — which deliberately holds no candidate list, because the design document quotes that file and the alternatives stay in the design space — and the whole scored candidate set, with a reproducible `candidateSetSha256` fingerprint over it, to `out/detailed/matrix_vector_candidates.json`. That second file is what a consumer which merges, ranks or excludes candidates is checked against: a winner-only artifact cannot support "every exclusion is traceable", since the excluded entries were never written down. Prints the per-option comparison and the analysis tables for the document. Reads the published point from the baseline, so run it after `baseline:sync`.
- `generate_comm_core_design.js`: Comm Core design search (HW-07, `teams/hardware/docs/10_COMM_CORE.md` section 7) over the design space `teams/hardware/inputs/comm_core_design_space.json`: enumerates every combination of the searched dimensions, adds each candidate's control path (trigger, graph fetch, WQE dispatch, doorbell, completion) to every collective class, keeps candidates within the spec tau, the SRAM capacity and the utilization limit, and ranks them by AI Core time, spec slack and area. Writes only the winner to `out/detailed/comm_core_design.json` and prints the best candidate of every option for the document. The ranked candidate head goes to `out/detailed/comm_candidates.json`, which is what `design.comm` reads: a winner-only artifact cannot support "every exclusion is traceable". This grid enumerates 216000 combinations and scores 45900 where the siblings score hundreds, so that file is the one place in this repository where the listing is knowingly truncated (`listed` / `truncated`) — the `candidateSetSha256` fingerprint is taken over the whole scored set and `infeasibleByCause` counts every excluded candidate by its violation set, so neither "these are the candidates that were searched" nor "why was X dropped" depends on the listing. Reads the published point from the baseline, so run it after `baseline:sync`.
- `generate_memory_design.js`: MC / Memory Cube design search (HW-04, `teams/hardware/docs/04_MEMORY_SUBSYSTEM_MC.md` section 5.1) over the design space `teams/hardware/inputs/memory_design_space.json` (MC tier, cubes per card, capacity per cube, bandwidth route, ECC overhead): scores every combination on a K3 detailed replay, keeps candidates that hold the published TPS/usr within tolerance and clear the program goal, the package placement window, the die area limit and this domain's card power caliber — where the card power is `8 x die + MC + the fixed 80 W` and deliberately does NOT charge the shared-port term the physical domain adds, so 2800 W is a looser check here by exactly 21.915648 W — and ranks them feasible-first, then by manufacturing risk class, then card-level MC power. Writes the winner to `out/detailed/memory_design.json` (no candidate list: the design document quotes that file and the alternatives stay in the design space) and the whole scored candidate set, with a reproducible `candidateSetSha256`, to `out/detailed/memory_candidates.json`. A route the search did not model is excluded by violation, not left to lose a tie-break on price. Reads the published point from the baseline, so run it after `baseline:sync`.
- `generate_physical_design.js`: Package / power / RAS design search (HW-09, `teams/hardware/docs/09_PACKAGE_POWER_RAS.md` section 3) over the design space `teams/hardware/inputs/physical_design_space.json` (process, matrix density, cooling, keep-out fraction): enumerates every combination, checks area conservation (`placed + keep-out <= 5248 mm²`, tolerance 0), the die area and power limits, the package placement window, the PHY shoreline and a K3 detailed replay, and ranks them feasible-first, then by the most conservative keep-out premise, then the largest reserve within that premise, then die power margin, then process risk. The keep-out is the share of the window that is LEFT OUT (published 0.1254 = 658.29/5248), not a usable share — reading it backwards inverts every area number. The most conservative premise outranks the largest reserve on purpose: 0.10 is numerically feasible but asserts a smaller keep-out than anything in the repository supports. Writes the winner to `out/detailed/physical_design.json` and the whole scored candidate set, with a `candidateSetSha256`, to `out/detailed/physical_candidates.json`. Reads the published point from the baseline, so run it after `baseline:sync`.
- `models/detailed_run.js` and `models/direction/run_directional_tps.js` were retired and deleted (ADR-0006); use `npm run model:planning`.
