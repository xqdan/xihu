# ADR-0028：算力核定义改为 L 1×512×8（8T）/ H 128×256×1（64T），发布点 1138.48 → 1043.96 TPS/usr

- 日期：2026-10-26
- 状态：`ACCEPTED`（定义）；**发布点下降是定义变更的直接结果，不是调优结果**。AC-1 仍未通过，缺口变大（见「后果」）
- 修订：ADR-0021（唯一硬件规格的核定义）、ADR-0026（发布点数字）、ADR-0027（不变，仅被引用）
- 来源：用户指令「Hcore 用 64T（256*128）这个，Lcore 用 8T（64*64）FP8，请修改下算力定义」，经两次确认：**64T / 8T 就是 FP8 峰值（不再乘 2）**；**L 改成长条状**

## 背景

此前的核定义是 L 核 `1×256×8`（2048 MAC，4.10 TFLOPS）、H 核 `48×128×6`（36864 MAC，73.73 TFLOPS），每 Die 8 个 L + 4 个 H，合计 327.68 TFLOPS。
用户要求的定义是每核算力：

| 核 | 形状 | MAC | 峰值（1 GHz，2 FLOP/MAC） |
|---|---|---:|---:|
| L | `1×512×8`（长条） | 4096 | **8.19 TFLOPS**（"8T"） |
| H | `128×256×1` | 32768 | **65.54 TFLOPS**（"64T"） |

核数不变（8 L + 4 H），所以**每 Die 总算力仍是 327.68 TFLOPS**：8×8.19 + 4×65.54。这是一次 L/H 之间的形状重分配，不是峰值变化。

## 决策

1. **核的形状与核数是定义，不是搜索维度。** `k3_rdma_final_tuning_search.js` 导出 `CORES`（`nL 8, nH 4, lRows 1, lCols 512, lEngines 8, hRows 128, hCols 256, hEngines 1`），`EXT` 中这六个字段各只有一个值。
2. **H 核取 128 行 × 256 列，而不是 256 行 × 128 列。** 这是对用户措辞「256*128」的一个**判断**，不是转写：

   | H 核朝向（同为 32768 MAC，65.54T） | 发布点 TPS/usr |
   |---|---:|
   | 256 行 × 128 列 | 860.61（低于目标） |
   | **128 行 × 256 列** | **1043.96** |

   原因在填充率。H 核的 `fill = min(1, m/hRows) × min(1, n/hCols)`，decode 下 `m = headTile`，而 `headTile` 上限 96（K3 只有 96 个头）。行数 256 时只填 0.375，行数 128 时填 0.75。
   **如果用户的意图确实是 256 行，需要另议；本 ADR 不假设它。**
3. **搜索的 KV tile 限制在联合悲观 tile 以下。** `KV_TILES = [4096, 8192, 16384]`，由 `JOINT_PESSIMISTIC.compute.kvTile`（32768）派生。
   不限制时搜索选 32768（1049.32 TPS/usr），与悲观 tile 相同，使压力项成为空操作（有无该项，悲观重放都是 903.09 / 892.77）。限制的代价是 5.4 TPS/usr（1043.96）。这条沿用了 `cae1b5e` 的结论：只有**更大**的 tile 才在时间与 H-local 容量两个轴上同时不利。
4. **耦合搜索的 `vectorLanes` 网格由规则 `laneSpan` 推导。** 取 `matrix_vector_design_space.json` 的合法档位中，介于计算赢家的 lanes 与发布 lanes 之间（含两端）的全部档位。
   手写列表 `[640, 704, 768, 832]` 写于 `ae253b5`，当时计算赢家与发布值都是 512；之后发布值升到 1024、计算赢家变成 576，网格从未重算，于是**既不含 576 也不含 1024**，无法回答它自己提出的问题（五个域赢家能否合成并胜过发布点）。
   推导结果落盘在 `coupling_candidates.json#designSpace.derived.laneSpan`，可复核。
5. **修两处崩溃。** `comm_core_search.js#protocolClasses` 与 `coupling_search.js#slowestCollective` 遇到模型因限值拒绝的行（没有 plan）会抛 `TypeError`。现在这类行的 B-TAU 记为 `null`（不可评估），该行因它自己的限值违规而不可行，不再崩溃。
6. **`sharedPortScaling` 从 `NO_EFFECT` 回到 `MECHANISMS`。** 在 1138.48 点它精确为零；在 1043.96 点回退它要损失 0.0046 TPS/usr。仍远低于它占的 7.78 mm² / 2.74 W，但不再是零。
7. **保留 H 核 64T（`128×256×1`）的定义，不削到 96 行。**（用户决定，2026-10-26）理由：H 核同时服务 prefill 和 decode。`hRows` 128 → 96 在模型里是「白省」（0.0 TPS，省 26.2 mm² / 31.5 W），但模型只建 decode B=1：那里 `m = headTile ≤ 96`，第 97–128 行填不满（填充率 0.75）。prefill 的 M 维是序列长度，不受这个上限约束，这部分 MAC 在 prefill 下是用得上的。**因此「白省」只是 decode 单侧的结论，不能当作可以削掉的依据。**

## 后果

### 数字

| | ADR-0026 点（`cae1b5e`） | 本 ADR | 变化 |
|---|---:|---:|---:|
| 发布点 TPS/usr | 1138.48 | **1043.96** | −94.52（−8.3%） |
| raw | 750.74 µs | 818.71 µs | +67.97 |
| 联合悲观点 `compute` | 941.51 | **837.08** | −104.43 |
| 联合悲观点 `allUnmeasured` | 926.52 | **825.28** | −101.24 |
| Die 面积 | 361.68 mm² | 372.53 mm² | +10.85 |
| Die 功耗 | 292.48 W | 295.09 W | +2.61 |
| 卡功耗 | 3047.90 W | 3068.79 W | +20.89 |
| 观测 keep-out 下的封装余量 | 96.47 mm² | **9.62 mm²** | −86.85 |
| 耦合联合点 | （存在） | 896 lanes，**1000.07** | 余量 0.07 |
| 最薄的单项余量 | 矩阵利用率 38% | bank 不均衡 **14.0%**（矩阵利用率 14.5%） | 换位且收窄 |

**追记（2026-10-27，`bc88b4b` / `3475d83`）：** 上表与风险 2 的耦合联合点是 `cae1b5e` 之后的第一次重耦合。矩阵:向量搜索加入 `inlineDequant` 后计算域赢家由 896 lanes 变为 384 lanes（1015.34 TPS/usr），按决策 4 的 `laneSpan` 规则重耦合，联合点落到 **`tauOverlapCompute:vectorLanes=640|commOverlap=true`，1001.74 TPS/usr，Die 333.89 mm²，封装余量 318.76 mm²**，五个域赢家的直接合成是 982.89（仍低于 1000）。联合点仍要靠耦合阶段否掉计算域赢家才能存在，余量由 0.07 增至 1.74，但这一结论对 `hRows` 128 与 `commOverlap` 的取值敏感（`out/detailed/coupling_design.json`，8 个可行行 / 8 个 Pareto 行）。

**AC-1（联合悲观点 ≥ 1000）仍未通过，缺口从 58.5 扩大到 174.7 TPS/usr。**

### 风险，按严重程度

1. **封装余量只剩 9.62 mm²。** 面积现在是比功耗更紧的边界（Die 功耗余量 4.91 W，卡功耗余量 131.21 W）。任何再让 Die 变大的改动都装不进窗口。
2. **耦合联合点是临界可行（余量 0.07 TPS/usr）。** 五个域赢家直接合成只有 937.58；联合点存在，是因为耦合阶段否掉了计算域的最省面积赢家（576 lanes）而改取 896 lanes。这不是「域赢家能合成」，而是「域赢家加一次耦合修正能勉强过线」。
3. **H 核约 16T 在 decode 下用不上，在 prefill 下是否用得上没有被验证。** `hRows` 128 → 96 的边际是 **0.0 TPS / 0.0 TPS（悲观）**，却省 26.2 mm² 和 31.5 W：`headTile` 上限 96，第 97–128 行在 B=1 decode 下没有头可填，64T/核里约 16T（有效约 49.2T）属于这一类。
   用户已决定保留 64T（决策 7），理由是 H 核同时服务 prefill。**这条理由目前只是设计意图：模型里没有 prefill，没有任何产物显示这 16T 在 prefill 下被填满，也没有 prefill 与 decode 并行时的资源争用模型。** 代价是明确的、已经在数字里：Die 比 96 行多 26.2 mm²，Die 功耗多 31.5 W，封装余量因此只剩 9.62 mm²（96 行是 218.90 mm²）。这笔账是为一个未建模的用途付的。
4. **规划模型的标定变差。** 留出点 320/400/480/560 的残差为 −13.7 / −12.2 / −11.0 / −9.3%（ADR-0026 点：最大 26.9%，更差）。比上一版好，但 320/400/480 三档仍超出 10% 的门，只有 560 在门内。

### 测试

没有放宽任何判据。每处改动都是「断言的前提随定义失效，改为断言现在成立的事实」，并在测试里写明机制：

| 测试 | 变化 |
|---|---|
| `test_robust_search` | 「必须比 ADR-0026 之前的 921.63 更好」改为「钉住 837.08 / 825.28，且必须**低于** 921.63」——这是一次回退，断言防止有人改参考数字把它说成进步 |
| `test_k3_rdma_final_tuning` | 「depth 1 必须比 depth 2 贵」改为「发布点上 depth 1..4 完全相同；窗口紧的点上更深反而更慢」。FP8/softmax 耦合断言原本靠 1e-13 的浮点噪声通过，改为陈述真实状态（latent） |
| `test_matrix_vector_design` | B=1 GEMV 的解包上界只预测路由专家（184 个算子），稠密 GEMV（1025 个）被 local SRAM 读限住，该上界不建模 |
| `test_memory_design` | 半数栈位的损失 16.8% → 4.1%，且**刚过 1000（1000.71）**；`cubesNotSpec` 成为它唯一的违规，16 栈锁定不再有性能理由 |
| `test_planning_assumption_sensitivity` | 拟合 kMemory 1.4537 → 1.2182，落在两个 case（1.0 / 1.3）之间，两个方向都被覆盖；按槽位的 `bound` 判断是否随 kMemory 变化 |
| `test_final_search_parallel` | 形状固定后 `A.BASE` 不再需要修复，改用构造种子（`sharedSlices 32`，一步可修），并用仍自由的旋钮保持 256 个组合的缩减空间 |
| `test_coupling_workflow_behavior` | 三个可行行互不支配，产物里没有「被支配的可行行」；改为用真实 Pareto 行的 `pareto:false` 副本构造，机械核对读的正是这个字段 |
| `test_tps_attribution` | `kvTile 32768` 单独已超预算（955.79），`breaksOnlyTogether` 不再成立 |

## 未解决

1. **256×128 还是 128×256。** 见决策 2。
2. **H 核 64T 的 prefill 侧用途没有被建模。** 保留 64T 是用户的决定（决策 7），但它的依据（prefill/decode 并行使用）在模型里没有对应：没有 prefill 的 H 核填充率、没有并行时的 shared SRAM / NoC / 功耗争用。记在 `OPEN_ISSUES.md` O-024，与 O-011（Decode/Prefill 是否同卡共部署）相关。
3. **联合点 0.07 的余量。** 任何一个未测量参数都能抹掉它。
4. **`bank 不均衡` 成为最薄的单项余量（1.15 → 1.31）。** 它没有 RTL 或微基准依据。
5. **`die_area_reallocation` 的爬山提案放不进封装**（Die 383.7 mm²，缺口 −79.3 mm²），研究本身仍不扣 keep-out（已知口径差，未修）。
