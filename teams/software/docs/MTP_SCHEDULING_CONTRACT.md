# MTP / 推测解码调度契约

- 所有者：Software（调度）；共签：Hardware（验证单元支持）、Model（接受率证据）
- 状态：**探索**——MTP **不是**基线场景（`PRODUCT_REQUIREMENTS.md` FR-05）
- 权威来源：`integration/detailed/mtp_exploration.js`、`out/detailed/mtp_exploration.json`、
  21 号文档 §6.4、`OPEN_ISSUES.md` O-020(3)

## 0. 本文的定位：为什么给一个非基线场景写契约

MTP 在 21 号文档 §6.4 里是三条缩小联合悲观缺口的手段之一，但它**距离基线最远**：
它需要改变的是**每步 token 数与 KV 读取的对应关系**，而不是调一个参数。

本文的作用是：**在有人提议把 MTP 升级为基线之前，先把代价写在明面上**。
契约先立，场景后启——反过来做（先跑起来再补契约）会漏掉下面 §3 的两条前置。

## 1. 场景定义

| 项 | 值 | 说明 |
| --- | --- | --- |
| 验证 token 数 k | 1 / 2 / 3 / 4 | k=1 即当前基线 |
| 期望接受 token 数 | `(1 − a^k)/(1 − a)`（a=1 时取 k） | 几何近似 |
| 草稿层数 d | 1 / 2 层等效 | `draftLayerEquiv` |
| 裕量 | ×1.17 | 与基线同一口径，**只应用一次** |
| TPS 公式 | `1e6 · E[token] / ((verifyRawUs + (k−1)·d·layerUs) · 1.17)` | `mtp_exploration.js` |

其中 `layerUs = one.verifyRawUs / 93`（原始值，未乘裕量）。

## 2. 结果与结论（`out/detailed/mtp_exploration.json`）

验证开销（k=1 为 775.8 µs）：

| k | verify (µs) |
| ---: | ---: |
| 1 | 775.8 |
| 2 | 1012.9 |
| 3 | 1345.1 |
| 4 | 1700.6 |

MC640 下各接受率（BF16）：

| a | TPS/usr |
| ---: | ---: |
| 0.4 | 1172 |
| 0.6 | 1339 |
| 0.8 | 1531 |

**关键结论**：验证开销增长很快——k 从 1 到 2 就多 237 µs。
MTP 的收益完全取决于接受率 a，而 **a 从未被测过**。
在 MC640 以外（例如 MC480/MC400），需要 a = 0.4（MC480）或 a = 0.65（MC400）才达标，
且这还是在**接受率与专家路由不相关**的假设下。

## 3. 两条前置（缺一不可）

| # | 前置 | 为什么不能省 |
| ---: | --- | --- |
| 1 | **实测每 token 接受率** | `mtp_exploration.js` 用几何近似 `(1−a^k)/(1−a)`，这是简化模型；真实接受率随 prompt 与层数变化 |
| 2 | **专家路由相关性** | 本模型隐含"接受 token 与专家路由独立"。实际上被接受的 token 与草稿 token 高度相关，**路由也会相关**——这会让验证步的专家加载量偏离模型预测，方向不确定 |

**第 2 条是最容易被漏掉的**：它不是精度问题，是模型结构问题。
在相关性未知的情况下，本探索给出的 TPS 区间（BF16 MC640 外需 0.25–0.8 接受率）**不能作为决策依据**。

## 4. 调度契约（若升级为基线，必须成立）

| # | 条款 | 说明 |
| ---: | --- | --- |
| C-1 | **`seqs` 与 `tokens` 语义分离** | 验证 token 共享同一次 KV 读取：KV 任务按 `SQ`（序列数）计费，而 Q/O/residual/route/dispatch 仍按 `B` 计。见 `k3_operator_sram_sim.js` 的 `seqs` 参数与校验 `1 ≤ SQ ≤ B` |
| C-2 | **确定性** | 相同输入与相同 k 必须逐位可重现（FR-08）；接受/拒绝路径不得引入非确定性 |
| C-3 | **KV cache 一致性** | 拒绝的 token 必须能回滚 KV 写入；KV cache 是 FP8 存储，回滚不得改变已接受部分的位模式 |
| C-4 | **退化路径** | a 过低时（如 < 0.2）必须能退到 k=1，且退化不改变输出语义 |
| C-5 | **精度** | 草稿模型与验证模型的 dtype 必须符合 `PRECISION_POLICY.md`；接受判据（argmax 比较）本身是新的精度决策，需走精度签核 |
| C-6 | **批量与 TP32 交互** | B=1 时 MTP 改变的是"每步 token 数"；TP32 下 393 次集合通信的次数会随 k 变化，**通信账必须重算**，不能沿用基线的 393 |

**C-1 已在模型里实现并有校验**（`k3_operator_sram_sim.js` 与 `k3_architecture_search.js` 的 `scoreTokensPerCore`），
C-6 尚未在任何地方评估——它是对 393 这个数字的直接冲击，而 393 是 τ 敏感度的乘数（τ 余量每次仅 0.201 µs）。

## 5. 升级为基线的判据

只有全部满足才能提议升级（需 ADR）：

1. §3 两条前置有实测证据；
2. §4 六条契约全部有实现与测试；
3. C-6 的通信账重算完成，且 τ 余量在新账下仍成立；
4. 联合悲观点在 k>1 下重新计算并 ≥ 1000（AC-1 的口径不因场景变化而放松）；
5. `PRODUCT_REQUIREMENTS.md` FR-05 与 `SCENARIO_MATRIX.md` 同步修改。
