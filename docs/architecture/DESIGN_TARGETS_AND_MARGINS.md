# 设计目标与余量（下达给下游的指标）

- 所有者：Council（指标）/ 各单元负责人（认领）
- 状态：`BASELINE`
- 权威来源：[21_TPS_DESIGN_BASELINE.md](21_TPS_DESIGN_BASELINE.md) §6.1 / §6.1.1、
  `teams/hardware/inputs/k3_mc_baseline.json#tpsDesign.sensitivity`、
  [`PRODUCT_REQUIREMENTS.md`](PRODUCT_REQUIREMENTS.md) §3

## 0. 本文的用途

21 号文档第 6.1 节列出了**哪些参数没有被测量**，以及它们各自能偏到多远才跌破 1000。
那些数字原本是**回顾性的**：模型跑完了，回头算还能偏多少。

本文把它们转成**下达性的**：每个单元负责人拿到的是一条指标线，以及「你的参数跌破这条线，整颗芯片就跌破目标」。

两处必须区分：

| | 回顾（21 号文档） | 下达（本文） |
| --- | --- | --- |
| 问的问题 | 这个参数偏到多少会跌破？ | 你必须保证这个参数不低于多少 |
| 用途 | 说明余量有多少 | 写进单元设计规格与签核条件 |
| 失效后果 | 读到一个数 | 触发变更评审 |

## 1. 目标线（必须同时成立）

| 目标 | 值 | 依据 | 判据级别 |
| --- | ---: | --- | --- |
| 发布点名义 TPS/usr | 1101.77 | `tpsDesign.point` | `MODEL`，**不是验收判据** |
| 联合悲观点（Die 侧） | ≥ 1000 | `JOINT_PESSIMISTIC.compute` 当前 921.63 | **主判据**（AC-1） |
| 联合悲观点（全部未测量） | ≥ 1000 | `JOINT_PESSIMISTIC.allUnmeasured` 当前 906.51 | **主判据**（AC-1） |
| raw 预算 | 854.70 µs/token | 由 1000 TPS/usr 与 ×1.17 裕量推导 | 时间账约束 |
| 当前 raw 余量 | 78.95 µs | 854.70 − 775.75 | 设计余量 |

**缺口**：联合悲观点离 1000 差 93.49 TPS（allUnmeasured）。缩小缺口的杠杆见 §4，两者都不是基线。

## 2. 逐参数的指标线（下达）

下表把 21 号文档 §6.1 的盈亏点转成指标。每个参数有**四个值**：发布值（模型当前用的）、
悲观端（联合悲观点用的）、盈亏点（单独偏到这里就跌破）、以及下达到单元的**设计指标**。

设计指标的取法：盈亏点向发布值方向回收 15% 的安全余量，向下取整到便于实现的刻度。
**这只是本文的建议**，各单元可在签核时提出更严的值，不能更松。

### 2.1 计算侧（`JOINT_PESSIMISTIC.compute` 的成员）

| 参数 | 发布值 | 悲观端 | 单独盈亏点 | **下达指标** | 责任单元 | 证据现状 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| `A.TECH.matrixUtil` | 0.65 | 0.5 | 0.44 | **≥ 0.60** | HW-02 AI Core | `ASSUMPTION`（B-006） |
| `A.TECH.vectorUtil` | 0.35 | 0.25 | 0.14 | **≥ 0.30** | HW-02 AI Core | `ASSUMPTION`（B-006） |
| `A.TECH.unpackParamsPerLaneCycle` | 2 | 1 | 0.82 | **≥ 1.5** | HW-02 AI Core | `ASSUMPTION`，无 RTL 或微基准 |
| `A.TECH.layoutImbalance` | 1.15 | 1.3 | 上界 1.42 | **≤ 1.30** | HW-03 TMA/SRAM | `ASSUMPTION` |
| KV tile | 32768 | 16384 | 不适用（可调旋钮） | 见 §3 | SW-03 Kernel | `MODEL` |

关于 `layoutImbalance`：它同时是 **H local tile 的容量系数**。升到 1.8 是**不可行**（H local tile 放不下），不是变慢。
因此这一项的正确读法是"必须 ≤ 1.42 否则芯片不工作"，而不是"性能下降"。下达指标取 1.30 已相当靠近该硬边界，
签核时若 memory compiler 给出更大的不均衡，必须立刻走变更评审，不能就地接受性能损失。

关于 `unpackParamsPerLaneCycle`：它没有任何 RTL 或微基准依据，而 **L core 的 kernel 正是被它而不是被 MAC 限住**。
这是全部下达指标里证据最薄的一项（见 `VV_MEASUREMENT_PLAN.md` #3）。降到 1 时 TPS 为 1033.36，看似仍有余量，
但那是在其他参数都乐观的前提下；在联合悲观点里它是成员之一。

### 2.2 内存与软件侧（`JOINT_PESSIMISTIC.allUnmeasured` 额外成员）

| 参数 | 发布值 | 悲观端 | 单独盈亏点 | **下达指标** | 责任单元 | 证据现状 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| `A.TECH.mcUtil` | 0.70 | 0.65 | **0.63** | **≥ 0.68** | HW-04 Memory MC | `ASSUMPTION`（B-003、B-006） |
| 专家预测命中率 | 0.8 | 0.7 | 降到 0.3 仍成立 | **≥ 0.75** | SW-06 / HW-02 | `ASSUMPTION`（B-003） |
| `OPT.launchScale` | 0.45 | 0.7 | — | **≤ 0.6** | SW-01 Runtime | `ASSUMPTION`（B-003） |

**`mcUtil` 是最薄的一条。** 从 0.70 降到 0.63 就跌破 1000，而它是 spec 里的一个常数，
不是 MC 的带宽档位（第 1 节的 MC640 风险之外的**另一层**风险）。这个数在仓库存了两份：
详细模型读 `A.TECH.mcUtil`，规划模型读 `bandwidthTiers.sustainedEfficiency`，
`tests/regression/test_tps_design_baseline.js` 要求两者相等——**这条一致性测试必须保持**。

`launchScale` 的语义是"批量摊薄后保留下来的发射开销比例"，指标的写法与利用率类相反：**越小越好**，
但它是未回标的假设，从 0.45 涨到 1 会让 TPS 掉到 1088.47。

### 2.3 物理与外部依赖（不在联合悲观点内，但是 BLOCKER）

| 项 | 目标值 | 盈亏点 | 类型 | 责任 |
| --- | ---: | ---: | --- | --- |
| τ（每次集合通信时延） | 1.15 µs | **1.35 µs**（每次余量 0.201 µs） | `BLOCKER`（B-008） | Comm Core / PHY |
| MC 带宽 | 640 GB/s/颗 | 560 GB/s 时仅 977.00 | `BLOCKER`（B-002） | Memory MC |
| 频率 | 1.0 GHz | 不得降频换算力 | `BASELINE` | 实现 |

τ 的余量是**每次集合通信 0.201 µs**。通信占 raw 的 53%（451.95 µs = 393 × 1.15），
因此 τ 是本项目**最敏感的单点**：它没有物理推导，而把它从 1.15 抬到 1.35 就等于把发布点降到 1000。

## 3. 旋钮类参数的指标（不是越严越好）

有两类参数是**设计旋钮**，不适用"≥ 某值"的写法：

| 旋钮 | 发布值 | 限制 | 说明 |
| --- | --- | --- | --- |
| KV tile | 32768 | 16384 时 FP8 为 1094.35、BF16 为 1027.08；32768 时 BF16 **不可行** | 与 `kvCache` 耦合：dequant 走 H 向量 lane 并从 softmax 可掩盖预算中扣除 |
| 预取深度 `x.depth` | 4 | 取 2–4 同 TPS，取 1 降 1018.96 | 属于搜索空间，不在联合悲观点内 |

KV tile 记在这里是为了提醒下游：**降低 KV tile 不能换来 robust**，它同时降低 TPS 和容量。

## 4. 缺口的两个杠杆（均非基线）

联合悲观点离 1000 差 93.49 TPS。21 号文档 §6.4 / §6.5 给出两条**探索性**路径：

| 杠杆 | 效果 | 代价 | 前置条件 |
| --- | --- | --- | --- |
| Die 面积/功耗再分配（§6.5） | 悲观点 921.63 → 998.91（+77.3） | 卡功耗余量 55.1 W → 4.7 W（1.97% → 0.17%） | `vectorLanes=1024` 需向量单元与功耗模型签核 |
| FP8 稠密条件路线（§5.1.4 / O-020） | MC400 达 1080.78，MC 档位从 640 降到 400 | 依赖 B-001 / O-012 精度签核 | 精度验收通过（`PRECISION_POLICY.md` §6） |
| Batch=1 + MTP 验证（§6.4） | MC480 需接受率 0.4、MC400 需 0.65 | 接受率与路由相关性均未测量 | MODEL-03/04 实测 + 软件调度合同 |

**注意两条杠杆的关系**：FP8 稠密让 MC400 达标，从而不再需要 Die 面积再分配；
Die 面积再分配让**计算侧**悲观点接近 1000，与带宽路线独立。两者**可以叠加，但不必叠加**。
在 B-001 结论出来前，两个方向都要留活口——这是本节的结论，不是建议。

## 5. 余量纪律

1. **任何参数不得单独消耗掉它的全部余量。** 下达指标已按 15% 回收；单元若需进一步放宽，走变更评审。
2. **联合悲观点的成员不得被单独"优化掉"**：不能因为某项单独看还有余量就把它移出联合悲观点。
   联合悲观点的意义正是「每项单独都够、一起不够」。
3. **改动本文任一指标，必须同步**：21 号文档 §6.1、`PRODUCT_REQUIREMENTS.md` §3、
   `DESIGN_EVIDENCE_MATRIX.md`，并在 `00_CURRENT_STATE.md` 记录。
4. **重现**：`npm run search:final && npm run baseline:sync && node tests/regression/test_tps_design_baseline.js`。
