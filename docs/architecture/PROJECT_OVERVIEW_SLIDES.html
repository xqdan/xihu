01

驱动：为什么要这样做

两个痛点：架构决策靠经验拍板；往下的研发靠沟通对齐。 第 02 部分用可执行模型和多 agent 回答前者，第 03 部分用以设计文档为中心的流程回答后者。

Why · 痛点 1：架构阶段

经验拍板的芯片架构设计有什么问题

以往的架构设计，常常是一群人凭经验和感觉拍板。

细节覆盖不全

计算核、片上存储、互联、存储接口、封装、编译器、kernel、调度……没人能在脑子里同时装下全部细节。

说不清哪些细节重要

无法回答“这一项改动让最终 TPS 变了多少”，敏感项和余量都靠猜。

经验会带偏

上一代的经验在新的模型结构（MLA、线性注意力、稀疏注意力、MoE）上可能不再成立。

讨论变成观点之争

谁的声音大谁赢，而不是看数字；结论不可追溯、不可复现。

AI for Chip 的做法

  • 把架构写成可执行模型：spec 一改，TPS/usr 跟着变
  • 让多个 AI agent 各管一块，展开人装不下的细节
  • 用搜索在设计空间里选方案，备选和落选理由都留档
  • 用测试和 Gate 守住一致性，人只审查和拍板

每个结论都能追溯到
是哪一项、变了多少、证据是什么。

Why · 背景：谁和谁在沟通

芯片研发中的常见团队与交互

一颗芯片从定义到量产，通常要十几个团队接力；团队之间交换的主要是规格、约束和反馈。

定义

产品与算法（目标负载、指标）· 架构与性能建模

前端实现

微架构与 RTL 设计 · IP / PHY（SerDes、存储接口）· DFT

验证

RTL 验证（UVM / 形式化）· 指令与参考模型 · 仿真器、FPGA / Palladium 原型

软件

编译器 · runtime / 驱动 / 固件 · 算子库与模型适配

后端与制造

综合 / 布局布线 / 时序签核 · 封装与 SI / PI / 散热 · 硅后 bring-up 与量产测试

接口主要交互内容
产品 / 算法 → 架构目标模型与负载、TPS / 功耗 / 成本目标、算子清单与精度要求
架构 ⇄ RTL 设计模块划分、微架构规格、接口与 PPA 预算 ⇄ 实现可行性、面积与时序反馈
RTL 设计 ⇄ 验证设计规格、寄存器与协议 ⇄ 验证计划、覆盖率、bug 与规格澄清
架构 → 仿真器功能与周期行为（参考模型）；仿真器再作为验证的 golden model 和软件的早期平台
架构 / RTL ⇄ 软件ISA、寄存器、描述符格式、编程模型 ⇄ 可调度性、算子需求、易用性问题
RTL ⇄ 后端 / DFT网表、时序约束、floorplan、扫描与 MBIST ⇄ 时序违例、拥塞、面积、ECO
后端 ⇄ 封装 / 架构bump 与 I/O 岸线、功耗与热密度、供电 ⇄ 封装面积、互联带宽上限
硅后 → 全部团队bring-up 问题、errata、软件绕路（workaround）、下一代改进项

几乎每条接口交换的都是“规格 + 反馈”：规格一改，所有下游都要重新对齐——这就是下一页的沟通成本。

行业常见分工示意，不同公司的团队拆分和叫法不同
Why · 痛点 2：往下的研发

大量工作量产生于沟通，信息不透明埋下问题

芯片研发里写代码往往不是最慢的；最慢的是各团队对同一份规格对齐理解，以及规格变了之后没人知道。

今天：点对点对齐

架构、RTL、RTL 验证、指令验证、算子验证、仿真器、编译器与底软、后端，8 个环节两两沟通就是 28 条线。真实规格散落在 RTL、邮件、会议纪要和个人记忆里；文档落后于代码，同一句话各方理解不同。

目标：以文档为中心

每个环节只和文档对齐，8 条线。文档与 RTL 同源、同步变更；差异由机器检查发现，而不是等到联调或回片。

信息不透明规格分散、滞后、有歧义
➜
理解不一致RTL、验证、软件各按各的理解
➜
验证不充分测试计划按“理解”写，漏掉的正是误解处
➜
bug 埋在硅里联调、Palladium 或回片后才发现
➜
周期 delayECO、改版、软件绕路

关键点：验证只能发现“和验证工程师的理解不一致”的 bug；如果设计和验证读的是同一份含糊的文档、各自脑补，误解处恰恰没人测。

The chip, in brief

这次的对象：一颗大模型 Decode 推理芯片

芯片本身只是流程的第一个用例；这里只说它大致是什么、为什么难，不展开具体架构。

单用户吞吐

目标是每个用户每秒生成的 token 数（TPS/usr），而不是整机吞吐

模型已达标

当前发布点在模型里达到目标 MODEL，尚未物理签核

工作负载多个前沿 MoE 大模型的 Decode；单用户、超长上下文
系统多个封装组成一个张量并行副本，封装之间直接互访片上存储
封装多 Compute Die + 外置高带宽存储
Die 内异构计算核（矩阵 + 向量）、多级片上存储、数据搬运、片上网络、通信单元

为什么适合检验这套流程

  • 没有 batch 摊薄：每个 token 都要读一遍激活权重和长上下文，还要做数百次跨卡集合通信，上限由带宽和通信时延决定，不是峰值算力
  • 耦合强：存储带宽、通信时延、片上存储、预取、融合相互影响，只看单点会误判
  • 多个模型结构不同：多种注意力变体与 MoE，上一代经验不一定适用

Worked examples

两个实例：一个问题怎样走完流程

两项都不改发布点，结果都是 MODEL，等回标。

通信核：从瓶颈到新单元

  1. 发现：时间账显示通信占 raw 一半以上，时延下限没有物理推导
  2. 参考：业界公开的专用通信引擎设计
  3. 设计空间：放置、触发方式、描述符生成、下发、计数、存储…… 共 10 维
  4. 搜索：十万量级组合 → 数千可行 → 选出唯一方案，控制开销远低于预算
  5. 落地：单元规格文档、ADR（PROPOSED）、等待 RTL 回标

矩阵:向量配比：“32:1 还是 16:1？”

  1. 把问题变成准则：所有目标模型的每个 kernel，向量工作都要被矩阵时间掩盖
  2. 设计空间：向量 lane 数 × 低精度输入方式 × 指数单元
  3. 搜索：个位数可行 → 选出唯一配比；约束项来自某个模型的特定算子，而不是主力模型
  4. 落选理由：lane 少了掩盖失败或 TPS 下降；lane 多了功耗超限
  5. 结论带前提：只跑主力模型时需要的 lane 更少；原生低精度矩阵输入只有在面积开销低于某个阈值时才划算

Compare

两个层次：架构内的微调，和从需求出发的架构搜索

低降速仿真器在一个确定的架构上做微调、迭代；agent 流程把需求接到实现，架构本身是待定的输出，搜索范围横跨候选架构、并行度、存储档位和接口。

降速（slowdown）= 仿真耗时 ÷ 真实硬件耗时。降速越低，仿真跑得越快：微调需要它足够低才迭代得动，宽搜索需要它足够低才枚举得完。

固定的架构内：微调与迭代

  • 架构是输入，已经定好；改的是参数
  • 工程师提假设 → 仿真验证 → 再改一版
  • 回答"这台机器怎么调到最好"

从需求到实现：跨架构搜索

  • 架构是输出，待定；需求、约束、目标是起点
  • 先列全候选 → 逐个回放 → 排序 → 选出唯一方案
  • 回答"该造一台什么样的机器，以及为什么不是别的"
固定的架构内：微调与迭代从需求到实现：跨架构搜索
搜索对象已定架构下的参数：tile、buffer、流水、时钟架构本身：候选结构、并行度、存储档位、接口与拓扑
空间大小单点邻域，几十个组合；靠迭代收敛跨层次，十万量级组合；靠枚举与排序收敛
结论的形式这个架构下最优的一组参数定成什么架构 + 每个落选方案的落选理由
精度要求要高：微调的收益本来就小，误差会淹没信号可先粗后细：粗筛要广度，定案前再细算
典型失败精确地算错了一个方案：输入架构本身不对假设不真：理由齐全，但建立在没回标的模型上
观点页；仿真器本身仍是唯一的数字来源

Rules

硬规则：让 AI 写出来的数字可信

agent 产出很快，风险是“看起来合理”的数字；这些规则都由测试强制，npm test 不过就不能合入。

① 每个数字都有来源和证据等级

ASSUMPTION 假设 → MODEL 模型推导 → PLANNING_ESTIMATE 规划估计 → MODEL_OBSERVED 模型观测 → SILICON_OBSERVED 实测

② 单一来源

硬件规格只在一份机器可读文件里；文档只引用，不另行定义数值。

③ 生成物不手改

out/ 全部由脚本重算，测试用 sha256 把生成物绑定到输入。

④ 一致性由测试强制

spec、搜索结果、规划模型、contract、文档和看板不一致时，测试失败。

⑤ 不许靠口径变化宣称收益

经验增益因子全部为 1；任何折扣都要有事件/资源模型或实测证据。

⑥ 改规格要走 ADR

每个架构决策一份 ADR；TPS、功耗或面积变化超过阈值进入变更评审。口头确认不能关闭 BLOCKER。

来源：README.md、14_TPS_OBSERVATION_METRICS.md、OPEN_ISSUES.md「关闭纪律」

自然语言文档没法被机器比对；匹配关系要靠生成和追踪两种手段落实，并在 CI 里持续检查。

四条规则

  • 能生成的就生成：端口、位宽、寄存器、参数、descriptor 编解码从同一份结构化 spec 生成，一处改、处处变
  • 不能生成的就追踪：状态机、背压、错误和复位流程逐条对应 RTL 位置、断言和测试
  • 双向同步：RTL 改了文档没改，CI 失败；和今天“文档必须引用 out/ 存档数字”的测试是同一机制
  • 反向解释：让 AI 从 RTL 反推行为说明，与原 spec 做 diff，找语义漂移

独立性：别让同一个误解同时写进设计和测试

写 RTL 的 agent 和写验证 / 参考模型的 agent 必须分开，各自只读 spec，不读对方的实现。 否则两边共享同一个误解，测试全过、bug 仍在。

本项目的 V&V 已按这个原则组织：只能阻止 Gate，不能改被测团队的输入；参考模型（可执行模型、mailbox 生命周期、LSE 合并语义的单元测试）和 RTL 应分属不同 agent。

Review

Review：这条路线成立的前提与风险

方向是对的：信息透明和同源是芯片研发提速的关键。下面是要提前处理的六个问题，以及如何衡量“真的简化了”。

文档必须可检查

自然语言 spec 无法机器比对。接口、寄存器、参数、时序、状态机要结构化，文字只解释意图。

AI 的错误会相关

同一个 AI 写 spec、RTL 和测试，会共享同一个误解。参考模型和验证要独立来源、独立 agent。

文档量会爆炸

文档是视图，不是源：表格和数字从结构化 spec 生成；否则维护成本只是从代码转移到了文档。

端到端发现得晚

不能替代单元验证和形式验证；用例贯穿各层，但定位要靠分层测试和时间账。

人审查会成为瓶颈

AI 产出越快，审查越吃紧。按风险分级，把人力集中在接口、边界条件和签核上。

工具和 IP 的边界

综合、STA、形式、DRC 仍由 EDA 签核；PHY、存储接口、SerDes 等外购 IP 的文档来自供应商，也要纳入同一追踪体系。

怎么衡量是否真的简化了

跨团队澄清问题数 · 文档与 RTL 漂移数 · bug 发现阶段分布（逃逸到 Palladium / 硅片的比例） · 覆盖率闭合时间 · spec 变更传到全链路的时间 · 回片前后 bug 数 · 软件就绪时间相对硬件的滞后

评审意见；指标为建议，尚未在本项目中度量

  6. 端到端：一层 decode 的各类集合通信在 RTL 仿真中跑通，与时间账对账

为什么选它

控制开销的模型值远低于预算上限；但有两项备选只差纳秒级余量，回标后可能翻转——正好检验“回标 → 重搜 → 改设计”的闭环。

试点的退出条件

spec 条款 100% 可追踪到 RTL 和测试；文档与 RTL 漂移为 0；覆盖率闭合；周期模型与 RTL 误差在容限内；通信时延下限拿到控制路径一项的实测依据。

之后

按同一模板推广到存储、互联、计算核；Tile IR 成为编译器、仿真器和 RTL 的共同输入。

Roadmap

流程路线：从规划估计走到硅片实测

芯片按 P0–P7 逐级冻结；流程本身也要一步步补齐，让每一级冻结都有模型和测试撑着。

近期 · P0–P2（约 0–8 周）

  • 其余 agent 的设计也改成“设计空间 → 搜索 → 唯一方案”，Final Tuning 搜索是下一个候选
  • 把 W1 规格定级写成 agent workflow（D1–D6 并行 → D7 → A0），产物接 stage_a.js
  • Stage B 事件回放接入，Q-Gate 槽位从 PLANNING_ESTIMATE 走向 MODEL_OBSERVED
  • 关闭模型结构和存储档位两个阻塞项，在选定档位下达到目标并留出冻结余量

中期 · P3–P6（约 6–24 周）

  • 单 Die → 单封装 → 多封装副本逐级冻结，每级都由模型给出余量
  • 统一 Tile IR：编译器、模拟器、固件和 RTL 用同一份描述
  • 通信核（PROPOSED）试点：文档 → RTL → 验证 → 回标走通全链路
  • 综合、floorplan 回标面积功耗；全部 BLOCKER 有关闭证据

长期 · P7 之后

  • RTL 与 Palladium trace 回灌模型参数
  • 硅片实测把模型校准到 SILICON_OBSERVED
  • 同一套流程和模型用于下一代芯片：换模型、换工艺、换存储都是改参数重跑

什么时候算“流程可以支撑进入 RTL”

性能模型不再依赖未解释的全局经验缩放 · 选定档位在时间账里达到目标并留出冻结余量 · P99 与最坏情况通过 · 所有 BLOCKER 有关闭证据 · 规格可直接分解为 RTL、IP、firmware、compiler 和验证工作包

Summary

总结

一句话：把芯片架构设计变成一个可执行、可追溯、会随研发变准的模型，由多个 agent 协作推进；再以设计文档为中心，把同样的方法延伸到 RTL、验证、软件和后端。

驱动

两个痛点：架构决策靠经验拍板，装不下全部细节、说不清敏感项；往下的研发靠沟通对齐，信息不透明导致验证不足、bug 埋得深、周期拖期。第一个用例是一颗大模型 Decode 推理芯片。

流程

可执行模型 + 时间账；人给起点，agent 搜索设计空间，out/ 只放唯一方案；按团队切分的多 agent，任务卡进、handoff 出；按设计目的组成 workflow，两道 Gate 判完成；证据等级与单一来源，测试守恒、失败改上游。

向下延伸

以详细设计文档为唯一真源：文档完整、与 RTL 可检查地匹配、工程师在每个关口对齐理解、端到端用例贯穿各层。先用通信核走通全链路。

长远目标

用 RTL、Palladium、综合和实测逐项替换假设，最终得到对着硅片校准的模型；流程和模型服务下一代芯片。
