01 · 设计目标

一个很窄、但很硬的目标

项目口径
工作负载K3 工程 preset：93 层、92 MoE 层、896 experts / Top-16、24 层 MLA + 69 层线性 Attention；GLM-5.2、DeepSeek-V4-Pro 为规划输入
场景单用户 Decode，Batch=1，Context = 1,048,576 token
并行TP=32 张卡（每卡一个封装），PP=1
目标1000 TPS/usr ⇒ 端到端 ≤ 1 ms/token；扣 1.17 工程裕量后 raw ≤ 854.7 μs
门槛架构冻结要求 ≥ 1050 TPS/usr，P99 不低于 1000
为什么难

93 层摊下来每层约 9 μs。每个 MoE 层 4 次 all-reduce，每个 MLA 层再加一次 LSE 合并，一个 token 约 400 次跨卡归约。1M context 的 KV 每 token 都要读一遍。三样东西同时卡在微秒级：MC 带宽、归约延迟、算力。

当前结论（P1 可执行模型）
  • 参考 MC 320 GB/s/颗：约 534 TPS/usr，明显不达标
  • Stretch MC 640 GB/s/颗：约 859 TPS/usr，仍未达标
  • 首要矛盾是可制造的 MC 聚合带宽，不是算力

02 · 芯片架构

一卡 = 一个 7-reticle 封装 = 一个 TP rank

单用户 Decode
└── 32 张卡（TP32，PP1）
    └── 1 张卡 = 1 个封装
        ├── 8 × Compute Die（约 400 mm²，2×4 排布，UCIe mesh）
        │   ├── L-Core：线性阵列，GEMV / 专家 GEMM
        │   ├── H-Core：Attention QK/PV、高复用 GEMM
        │   ├── Vector：RMSNorm / RoPE / Softmax / 路由
        │   ├── TMA + Local SRAM + Shared SRAM 切片
        │   └── NoC + Reduce + UCIe / RDMA gateway
        └── 16 × Memory Cube（3D-DRAM，每 Die 本地 2 颗）

固定的设计原则

  • 外置 Memory Cube：MC 只管容量与带宽，矩阵计算留在 Compute Die（近存计算是备选路线，不混入）
  • 显式数据搬运：Tile Descriptor、TMA、epoch、mailbox，不做 CPU 式隐式 cache coherence
  • 远端 SRAM 可寻址：RDMA 直写对端 SRAM，write→commit/ready→consume→ACK→release 生命周期
  • 分层归约：Core → Die → 8 Die 卡内 → TP 组；LSE 用 m/l/O 语义，不是普通 FP32 sum
  • 以 tile 为单位做抢占、同步和性能核算

两个并行维护的 profile

Profile用途规格
P0 物理主候选封装、面积、PPA 规划8L+8H/Die，1.0 GHz，96 MiB SRAM/Die
P1 可执行候选搜索与回归模型由搜索决定，当前 24L+8H，1.0 GHz，88 MiB/Die

04 · 设计思路

不从算子级精确模型起步，而是两层闭环

Stage A · 方向级（粗粒度）算术强度 + 带宽 + 归约延迟 + 粗算力 + 7R 面积约束 → 在规格网格上找"达标的最少卡数"，输出候选与方向判断
→
D-Gate独立校验器：三模型可比、面积守恒、敏感性扫描完成、候选 ≤ 3
→
Stage B · 参数级（细粒度）逐算子 FLOP/byte、tile、SRAM、DMA、NoC、collective、调度 → 事件回放 → 细 TPS、P99、PPA
→
Q-Gate只有 validated event timing 才能通过；合成事件永远 blocked
Stage A 回答的是"方向"
  • 瓶颈是带宽、算力、通信还是面积主导？
  • 7 个 reticle 下，Die、MC、PHY、热预算有没有可行组合？
  • L / H / Vector 的数量级怎么分？
  • TP8 / 16 / 32 哪个方向值得细化？
  • 哪些软件优化改变方向，哪些只改常数项？
Stage B 回答的是"数"
  • 每个算子在具体 tile 和资源上花多少 μs？
  • 带宽、队列、拥塞、集合通信同时满足吗？
  • 粗略 TPS 在算子级回放里成立吗？
  • P0 / P1、MC320 / MC640 的结论可复现、可制造吗？

Stage B 不达标 → 回流 Stage A 淘汰或调整候选，不允许直接改 Gate 状态。

05 · 粗粒度建模

规格网格 + 每层四拍时间线

规格维度（每个点单独优化部署）

维度档位
MC 数量8 / 16 / 24 / 32 颗/卡
MC 带宽320 参考 · 400 · 480 默认上限 · 560 / 640 激进（GB/s/颗）
SRAM/卡128 … 2048 MiB（预取缓冲 + 常驻权重分开记账）
L-Core 算力65 … 524 TFLOPS/卡，H = 8×L 同比计面积
归约延迟@TP82 / 1.5 / 1.15 / 0.85 / 0.66 μs
卡数16 … 256，取第一个达标的 N*

硬约束：SRAM 面积 + 张量阵列 + MC PHY + 固定开销 ≤ 8×400 mm²；权重 + KV ≤ 每卡容量。

每卡每层的时间账

MC 读下一层 → SRAM 预取缓冲 → 计算 → all-reduce

有效带宽 = 颗数 × 每颗带宽 × 0.70
MC 净读取 = (MC 读取 − SRAM 常驻节省) × PP
忙侧      = 计算 + 全部 TP all-reduce + 预测未命中补读
Stage     = max(MC 净读取, 忙侧)
E2E       = (PP × Stage + PP 跳 + LM Head) × 1.17
TPS/usr   = 1000 / E2E_ms
用它能得出的方向性结论
  • 归约延迟是"入场券"：≥1.5 μs 的芯片几乎不可能达标
  • 1M 的第一刀是 TP 把 KV 切开；16 卡撞 KV 带宽墙（约 883 TPS），32 卡才进入算力下限
  • 过线算力下限约 610 TFLOPS/卡，12 nm 级工艺够用，不必上 N7/N3

05 · 粗粒度建模

算术强度与 Roofline：把三个模型放到同一把尺子上

每个算子：
  I           = FLOP / byte
  ridge       = peak_FLOPS / effective_bandwidth
  bound       = I < ridge ? bandwidth : compute
  required_peak = FLOP/token × target_TPS
                 ÷ (utilization 0.6 × duty 0.85)
  ratio       = required / available
候选 TPS 上界 = target / max(ratio_compute, ratio_bandwidth)

K3 的算子 FLOP/byte 从 design_engine 的模型形状推导，并与校准的 RDMA tile 基线对账（FLOP 比 1.000，byte 比 0.979）。GLM / DeepSeek 目前是按比例缩放的占位，明确标 UNVERIFIED。

06 · 细粒度建模

算子 / tile 级离散事件模拟器

模型做了什么

  • 把 93 层展开成算子图：RMSNorm、投影、QK / online-softmax / PV、Router、Expert、Wup / Wdown、collective
  • 权重按 weight tile 切、KV 按 context tile × head tile 切，每个 tile 是一个 job，有生命周期（producer / consumer / last use）
  • SRAM 是显式容量池：分配、峰值、驱逐、预测命中 / 误读全部记账
  • DMA、compute、collective 三类事件按资源上限调度：TMA、Local / Shared SRAM 端口、NoC、MC、RDMA 链路
  • 输出每层 / 每算子的时间账、SRAM 峰值、每 token 外部读取字节、有效 DMA 带宽
op 时间 = max(FLOP/peak, read/端口带宽, write/端口带宽,
              unpack) + launch
comm 时间 = max(τ + bytes/link, bytes/SRAM 读, bytes/SRAM 写)

在此之上的 RDMA / collective 模型

  • 每次 collective 展开为 31 个 peer 的一侧写：issue → 串行化 → visible → ACK，带 outstanding 上限和 credit 回收
  • Mailbox 是验证模型：WRITE ≠ READY（要 commit），READY ≠ FREE（要 consume + 全部 ACK），防 ABA
  • LSE 归约按 m/l/O 合并，显式的 max / exp / sum

08 · 引入 AI 与 Harness

让 AI Agent 能安全地并行工作，靠的是 Harness 而不是提示词

Harness 的四层

1 · 边界AGENTS.md 定义团队目录 ownership、命名（HW/SW/MODEL/ARCH/VV-*）、不可做的事；一个任务只改一个模块及其测试与文档
2 · 契约机器可读 spec / manifest / contract JSON；单一事实来源（K3 形状只在 design_engine）；hash 绑定输入
3 · 验证33 个测试：物理守恒、单位、Roofline 复算、mailbox 生命周期、LSE 语义、一致性、链接 / require 结构、看板新鲜度、Gate 变异测试
4 · 治理Gate 由独立校验器计算；证据等级强制标注；ADR 记录方向变化；Backflow 而不是改结论

AI 在其中的角色

  • 专业团队 Agent：在自己的目录内生成规格、模型代码、契约，交付 artifact 而不是聊天记录
  • 集成 Agent：汇总候选、生成 scorecard、写 ADR，但不能改 Gate
  • 评审 Agent：像本次一样做代码 / 文档 / 数据一致性审查，找出自我认证、双重折扣、多重事实来源
  • V&V Agent：只写测试和校验器，不碰被测数据
这次审查暴露并修掉的典型 AI 协作风险
  • runner 直接写 decision: 'PASS'（自我认证）
  • 同一个 K3 在 manifest 与代码里是两个模型
  • 经验因子叠加、重复 key、双重折扣，把硬件能力"白送"
  • 文档手抄数字，多处漂移

对策全部是 harness 级的：单一来源 + 生成脚本 + 一致性测试 + 计算型 Gate。

10 · 小结

三句话

目标很窄：B=1、1M context、TP32 下 1000 TPS/usr，每层 9 μs，带宽、归约、算力三者同时卡在微秒级。
方法是两层闭环：先用算术强度 + 规格网格 + 四拍时间账定方向，再用算子 / tile 离散事件回放定数，Gate 由独立校验器算出。
AI 靠 harness 而不是靠信任：单一事实来源、hash 绑定契约、33 个一致性与守恒测试、证据等级、不能自我签核。
